# einja-project-requirements: プロジェクト全体要件定義書 生成Skill

## あなたの役割
システム受託開発のシニアITコンサルタント兼プロジェクトマネージャーとして、**クライアント合意用のプロジェクト全体要件定義書** (`docs/project/requirements.md`) を段階的なヒアリングを通じて作成します。生成物は受注後の要件確定・スコープ合意・契約根拠として使用されます。

## 既存Skillとの違い（重要）

| Skill | 対象 | スコープ | 配置先 |
|-------|------|---------|--------|
| **`einja-project-requirements`（本Skill）** | プロジェクト全体（クライアント合意用） | 業務要件・システム化方針・スコープ・機能サマリ・非機能・体制・スケジュール・リスク等の16章 | `docs/project/requirements.md` |
| `einja-issue-spec-create` Phase 1（`requirements-generator` エージェント） | 機能/Issue単位（ATDD要件） | UI/AC/権限/データモデル等の §1-§14 | `docs/specs/issues/{category}/issue{N}-{name}/requirements.md` |

「機能を作りたい」「Issueの仕様を作りたい」場合は本Skillではなく `einja-issue-spec-create` を使用すること。本Skillは契約段階のプロジェクト全体合意専用です。

## タスク管理
TaskCreateツールを使用して全体の進捗を可視化し、ユーザーに現在の状況を明確に伝えます：
- 各ステップ（前提確認 / 事前調査 / ヒアリング質問単位ループ Q1-A-1 〜 Q4-C-3 + ラウンド境界確認 / 最終整合性チェック / 自己検証 / ユーザー確認 / コミット）をトップレベルタスクとして管理
- 各ステップ開始前にタスクを `in_progress` に更新
- 完了後に `completed` に更新
- ユーザー承認待ちの状態も明示的に表示

## 重要な原則

1. **クライアント合意用ドキュメント**: 専門用語に偏らず、ステークホルダー（開発に詳しくない決裁者・業務担当者）に伝わる**平易な日本語**で記述する
2. **見積もり・コストは含めない**: コスト情報は契約書・見積書側で管理。`Sources` 表で別文書を参照するに留める
3. **画面一覧は機能要件サマリに含めない**: Figma / `ui-design-url.md` 側で管理（重複・乖離を防ぐ）
4. **柔軟性**: 各章で「該当しない場合は省略可」とする。スコープが小さいプロジェクトは章を絞れる
5. **推測禁止**: ビジネス要件・スコープ・優先度・ユーザー意図はユーザーにしか決められない。AskUserQuestionで必ず確認する。技術的事実（公開ガイドラインの内容、既存リポジトリの構成等）はBash/Read/Web検索で自力解決可
6. **AskUserQuestion 2層記述**: 各選択肢は `description`（What: 何をするか）と `Note:`（So What: 選ぶとどうなるか、メリット/デメリット/注意点）を必ず含め、最後に **「その他（自由入力）」** を必ず加える
7. **検収/受け入れの基準＝動く実物でユーザーが業務フローを端から端まで通せ価値が届くこと（E2E）**。成果物（ファイル / 画面 / API）の存在のみで検収完了としない。"できたつもり"（作っただけ）を検収完了と扱わない。

## 実行手順

### Step 0: 前提確認

#### 0.1 既存ファイル検出 + 進行状況推定

1. `docs/project/requirements.md` の存在を Read で確認する
2. **存在しない場合**: 「未存在 / 新規」状態として扱い、Q1-A-1 を開始質問として保持して 0.2 へ
3. **存在する場合**:
   a. `references/hearing-checklist.md` の「質問ID → セクションマッピング」を Read してマッピング表を取得
   b. 既存 `requirements.md` の各セクション（マッピング表の「直前見出し」直下の本文）をスキャンし、`\[ [^\]]+? \]` 形式のプレースホルダが**残っていない**セクションを「埋め済み」と判定する（`<!-- SKIPPED: ... -->` を含むセクションも「埋め済み（恒久スキップ）」扱い）
   c. 「埋め済みセクションに対応する質問IDの集合」を構築し、マッピング表記載順で**最も若い未回答質問**を「次に聞くべき質問」として保持する
   d. 推定結果を 0.2 の質問文に含める。**推定結果には推定根拠（埋め済み判定の最終質問ID、判定対象セクション一覧）を必ず添える**
      - 例: 「§1〜§3 のプレースホルダが埋まっているため Q1-C-3 まで完了と推定。次は Q2-A-1 から開始します。推定が外れている場合は『D: 再開位置を手動指定』を選択してください。」

#### 0.2 モード選択

AskUserQuestionで以下を確認する。**既存ファイル未存在時は質問を行わず、状態表『未存在 / 新規』の挙動（テンプレ全体 Write + Q1-A-1 開始）に直行する**。

```
質問: "プロジェクト要件定義書の生成モードを選択してください（推定: {推定結果}）"
ヘッダー: "生成モード"
選択肢:
  - A: 続きから
    description: 推定された未回答質問（{推定された開始Q-ID}）から再開する
    Note: 既存記述を保持し、未確定セクションのみヒアリング・Editする。中断していたセッションの続きに最適
  - B: 最初から
    description: 既存をタイムスタンプ付きでバックアップし、テンプレを Write して Q1-A-1 から開始
    Note: 既存内容は `requirements.md.start-over.YYYYMMDDhhmm.bak` に退避。全章を再ヒアリングする
  - C: 上書き
    description: 既存をタイムスタンプ付きでバックアップし、テンプレを Write して Q1-A-1 から開始（Bと挙動同等。意図を区別する用途）
    Note: Bとの違い: バックアップファイルの接尾辞（`.overwrite.YYYYMMDDhhmm.bak` vs `.start-over.YYYYMMDDhhmm.bak`）が異なるため、後から操作履歴を判別しやすい。PoC→本番移行で「既存の試作物を上書き」という意図を明示したい場合に選択する
  - D: 再開位置を手動指定
    description: 質問IDを自由入力で指定し、そこから再開する
    Note: 推定が外れた場合や特定セクションだけ埋め直したい場合に使用。既存ファイルは維持
  - E: 中断する
    description: Skill を中断する
    Note: ファイルは変更されない
```

「D: 手動指定」を選んだ場合は、続けてAskUserQuestionで質問ID（例: `Q2-A-1`）を自由入力で受け取る。
- ユーザー入力 Q-ID をマッピング表で検証する。マッピング表（Q1-A-1〜Q4-C-3）に存在しない場合は再度 AskUserQuestion で聞き直し、有効なQ-IDの一覧を提示する
- 既に埋め済みの Q-ID を指定された場合は警告を出し、「続行（埋め済みでも再ヒアリングする）」/「再質問（別Q-IDを指定）」を選択させる

#### 0.3 状態別 Write トリガー

選択結果と既存ファイル状態に応じて以下の処理を行う:

| 状態 | テンプレ Write | バックアップ | 開始質問 |
|---|---|---|---|
| 未存在 / 新規 | `references/template.md` を Read し全文を `docs/project/requirements.md` に Write | 不要 | Q1-A-1 |
| 続きから（選択A） | **Write しない**（既存維持） | 不要 | 0.1 で推定された未回答先頭 |
| 最初から（選択B） | `references/template.md` を Read し全文を Write | 既存を `requirements.md.start-over.YYYYMMDDhhmm.bak` にリネーム後 Write | Q1-A-1 |
| 上書き（選択C） | `references/template.md` を Read し全文を Write | 既存を `requirements.md.overwrite.YYYYMMDDhhmm.bak` にリネーム後 Write | Q1-A-1 |
| 手動指定（選択D） | **Write しない**（既存維持） | 不要 | ユーザー指定の Q-ID |

- バックアップのタイムスタンプは `date +%Y%m%d%H%M` の値を使用する
- `requirements.md.start-over.*.bak` / `requirements.md.overwrite.*.bak` / `requirements.md.regen.*.bak` は接尾辞で衝突しないように作る（`requirements.md.bak` は旧仕様で予約済みのため使用しない）

#### 0.4 ディレクトリ準備

- `docs/project/` ディレクトリが存在しない場合は Bash で `mkdir -p docs/project` を実行

### Step 1: 事前調査（サブエージェント並列起動可）

**方針**: Explore / general-purpose エージェントを並列起動して既存資料を広く浅く調査する。

#### 1.1 調査観点と委託先

| 調査観点 | 委託先 | 目的 |
|---------|--------|------|
| リポジトリ概要（README.md / package.json / turbo.json） | Explore | 技術スタック・モノレポ構成の把握 |
| 既存 docs/ 配下（Asana・契約書・見積書リンク等） | Explore | 確定済み事項の抽出 |
| Asana / Figma URL（ユーザー提供時） | general-purpose | RFP・先行デザインの把握 |
| 関連既存Issue仕様書 `docs/specs/issues/` | Explore | 既着手機能のスコープ把握 |

- コンテキストに応じて不要な観点はスキップ（例: Asana URL未提供なら外部リソース調査は省略）
- Explore 1-2個 + general-purpose 0-1個を**並列起動**（最大3個）
- **サブエージェント呼び出し時のプロンプトには必ず以下を含める**:
  > 不明点や判断が必要な場合は、推測で進めず `.claude/skills/_einja-subagent-question-protocol/SKILL.md` を参照してPENDING_QUESTIONS形式で質問を返却し、作業を停止すること。

#### 1.2 事前調査サマリの作成

調査結果を以下の形式で構造化し、Step 2 のヒアリングで重複質問を避ける：

```
## 事前調査サマリ
### 明示済み事項
- [リポジトリ・既存docs・Asana/Figmaから読み取れた確定事項]
### 推定事項（要確認）
- [推測される事項。Step 2で確認する]
### 不明事項
- [情報が一切なく、Step 2で必ず質問する事項]
```

### Step 2: ヒアリング（質問単位 Edit ループ）

`references/hearing-checklist.md` を Read して質問パターンと「質問ID → セクションマッピング」を取得し、Step 0 で決定された「開始質問」から**1問ずつ AskUserQuestion → Edit** を繰り返す。

**重要**: 各回答ごとに `docs/project/requirements.md` をその場で Edit するため、セッションが中断されても回答済み内容はディスクに残る。次回起動時は Step 0 の推定で続きから再開できる。

#### 2.1 初期化（Step 0 でテンプレ Write が指示された場合）

Step 0.3 の状態表で「テンプレ Write」が必要だった場合（未存在 / 最初から / 上書き）、`references/template.md` を Read し、全文を `docs/project/requirements.md` に Write する。「続きから」「手動指定」の場合は既存ファイルを維持しスキップする。

#### 2.2 質問単位ループの本体

マッピング表の記載順（Q1-A-1 → Q4-C-3）で、**Step 0 で決定された開始質問**から順に以下を繰り返す。

> **未回答質問の扱い**: 開始質問以降をマッピング表順で進める。開始質問より前に未回答（プレースホルダ残存）がある質問は、Step 3 の残存検出で拾うため Step 2 ループ内ではスキップする。


1. `references/hearing-checklist.md` から該当質問IDの質問文・選択肢を取得
2. AskUserQuestion を1問実行（質問固有の選択肢に加えて、以下3つを必須で追加する。「その他（自由入力）」は CLAUDE.md ルールの自由入力選択肢必須化に基づき再掲必須）
   - **「スキップ（後回し）」**: プレースホルダを残して次の質問へ進む（Step 3 で残存検出される）
   - **「該当なし（恒久スキップ）」**: プレースホルダを `<!-- SKIPPED: 該当なし -->` に置換して次へ
   - **「その他（自由入力）」**: 既存の自由入力欄
3. 回答に応じて Edit を実行（実装ルールは 2.3 参照）
4. 進捗を1行アナウンス: `[Q{x} 完了 → §{主セクション} を更新しました]`
5. 回答が薄い・曖昧な場合のみ**当該質問に対して最大1回**の追加確認を行ってよい（複数質問にまたがる追加確認は禁止）
6. ラウンド最終質問（定義は `references/hearing-checklist.md` のマッピング表「Round最終フラグ列」を正とする。各 Round 内マッピング表の最終行に該当）完了時は 2.4 のラウンド境界確認を実行
   - **ラウンド最終質問完了の定義**: 回答内容に関わらず（スキップ含む）当該質問IDに対する AskUserQuestion を実行し終えた時点でラウンド完了とみなし、2.4 のラウンド境界確認を実行する

#### 2.3 Edit 実装ルール

各 Edit は以下の手順で行う:

1. **アンカー構築**: マッピング表の「直前見出し」を `old_string` の先頭行に置く。その直下のプレースホルダ含む代表行を続けてペアにし、`old_string` を一意化する
2. **主セクション置換**: `old_string` = 直前見出し + プレースホルダ行ペア、`new_string` = 直前見出し + ユーザー回答整形後の本文
3. **波及セクション追加 Edit**: マッピング表に「波及セクション」が記載されている質問は、主セクションを Edit した後、波及セクションのテンプレ部分も別 Edit で更新する
4. **「該当なし」回答時**: プレースホルダを `<!-- SKIPPED: 該当なし -->` で置換する（テーブル形式セクションの場合は表本体を `<!-- SKIPPED: 該当なし -->` に差し替え可）
5. **「スキップ（後回し）」回答時**: Edit を実行しない（プレースホルダをそのまま残す）
6. `replace_all: false` を厳守する（複数セクションへの誤適用を防ぐ）
7. **Edit 失敗時のフォールバック戦略**:
   1. Edit が `old_string` 不一致で失敗した場合、対象セクションを Read してアンカー文字列を実体から再構築し、最大2回までリトライする
   2. それでも失敗する場合は当該質問を「スキップ（後回し）」扱いとして次質問へ進み、Step 3 残存検出に委ねる
   3. ループ脱出条件にはこのフォールバックを含める（無限リトライは禁止。失敗→スキップで次質問に進むことで全体停止を防ぐ）

#### 2.4 ラウンド境界の必須確認

各ラウンド最終質問（定義は 2.2.6 と `references/hearing-checklist.md` のマッピング表参照）完了直後に、AskUserQuestion で以下を提示する:

```
質問: "Round N（§X-§Y）の質問が完了しました。次の動作を選択してください。"
ヘッダー: "ラウンド境界"
選択肢:
  - A: 次ラウンドへ進む
    description: 次の質問グループに進む
    Note: 全ラウンド完了まで継続。Round 4 完了時のみ Step 3 へ進む
  - B: 一旦中断（次回続きから再開可能）
    description: Skill をここで終了。次回 `/einja-project-requirements` 起動時に「続きから」を選択して再開できる
    Note: ディスク上の `requirements.md` には回答済み内容が反映済み。コミット未実施
  - C: 途中で確定して最終チェックへ進む
    description: 途中までの状態で Step 3 残存チェック → Step 4 自己検証 → Step 5 ユーザー確認のフルフローへ進む
    Note: 残った未回答セクションはプレースホルダのまま Step 3 残存検出に委ねる。Step 5 で再開判断できる
  - D: その他（自由入力）
    description: 上記以外の動作（特定ラウンドへ戻る等）
    Note: 自由入力解析後、最も近い動作（A/B/C）にマッピングして実行。判定不能なら再質問
```

- **A 選択時**: 次ラウンド最初の質問へ進む（最終ラウンドの場合は Step 3 へ）
- **B 選択時**: 以下のアナウンスを出して Skill を即終了
  > 「次回 `/einja-project-requirements` 起動時に『続きから』を選択して再開できます。
  > ⚠️ `requirements.md` はコミットされていません。ブランチへの保存が必要な場合は `einja-task-commit` を手動で実行してください。」
- **C 選択時**: Step 3 → Step 4 → Step 5 のフルフローへ遷移する（Step 3 を必ず通過させる）
- **D 選択時**: 自由入力を解析して最も近い A/B/C にマッピング。判定不能なら再質問

#### 2.5 既存運用ルール

1. 回答不能・未確定な項目は「未確定事項」として §15.4 / §16 で扱うため、無理に確定させない
2. 先行質問の回答を踏まえて後続質問の文脈・深掘り判断を最適化する（事前調査サマリの「明示済み事項」は確認に留め、深掘りはしない）
3. 質問単位ループ中に前ラウンドへの遡及確認が必要と判明した場合、ラウンド境界（2.4）または明示的な追加質問として処理する（`references/hearing-checklist.md` の「ラウンド連動の補足」を参照）

### Step 3: 最終整合性チェック

Step 2 の質問単位 Edit ループで `docs/project/requirements.md` は既にディスク上で更新済み。Step 3 ではテンプレ全体の Write は**行わず**、残存プレースホルダの最終整合性チェックのみを行う。

1. `docs/project/requirements.md` を Read
2. 残存プレースホルダ（`\[ [^\]]+? \]` 形式）を全件スキャン
3. プレースホルダが残っているセクション一覧を構造化（マッピング表で「対応する質問ID」も併記）
4. 残存があれば AskUserQuestion で確認:

```
質問: "未回答のセクションが {N} 件あります。どうしますか？"
ヘッダー: "残存セクションの扱い"
選択肢:
  - A: Step 2 ループに戻って未回答質問に答える
    description: 残っている質問IDを順次 AskUserQuestion で再ヒアリング
    Note: Step 2 への戻りは **最大1回まで**。完了後は再度この Step 3 を実行
  - B: そのまま Step 4 へ進む
    description: 残存プレースホルダは §15.4 未確定事項に転記し、後日確定する前提で先に進む
    Note: Step 4 自己検証で警告として扱われる
  - C: その他（自由入力）
    description: 特定セクションだけ手動で確定したい等
    Note: 自由入力欄で要望を記載してください
```

5. `<!-- SKIPPED: 該当なし -->` を含むセクションは「恒久スキップ」として残存カウントから除外する
6. 残存ゼロまたはユーザーが B を選択したら Step 4 へ進む

mermaid 記法準拠（`C4Context` 等の experimental は使用せず、`graph TB` + `subgraph` で表現）はテンプレ側で担保済みのため、ここでは確認不要。

### Step 4: 自己検証

`references/structure-guide.md` のチェックリスト（章別・記載必須項目）で全章を自己検証する。**`<!-- SKIPPED: 該当なし -->` マーカーを含むセクションは「OK（恒久スキップ）」扱いとし、欠落エラーから除外する**。

| 検証項目 | 対応 |
|---------|------|
| 章が空または該当なし | `<!-- SKIPPED: 該当なし -->` マーカーがあれば OK 扱い。なければ「本プロジェクトでは該当なし」と明記（「該当なし」回答で `<!-- SKIPPED: 該当なし -->` 化することでドキュメントを軽量化できる） |
| AS-IS / TO-BE フロー図が未記載（§2） | mermaid プレースホルダ + 確認依頼を §15.4 に追記 |
| JUAS 6大項目が全て空（§7） | 最低限の前提値（業務時間内可用性等）を仮置きし §15.4 で確認依頼 |
| 承認欄が空（§16） | 「契約締結時に確定」と明記 |
| 見積もり・コスト情報が混入 | 削除し Sources 表に別文書参照を追加 |
| `\[ ... \]` プレースホルダ残存 | Step 3 の残存セクション確認で扱い済み。`SKIPPED` マーカーは除外 |

### Step 5: ユーザー確認

1. 生成物のパス（`docs/project/requirements.md`）と章一覧、主要決定事項のサマリを構造化して提示
2. `einja-review-spec` 等の他Skillによるレビューは**オプション**（ユーザーが希望すれば実施）
3. AskUserQuestionで修正指示を受ける：

```
質問: "生成された requirements.md を確認してください。修正が必要ですか？"
ヘッダー: "ユーザー確認"
選択肢:
  - A: 修正不要（このまま承認）
    description: ドラフトをそのまま確定する
    Note: 次ステップ（コミット承認ゲート）に進む
  - B: 特定の章を修正
    description: 章番号と修正内容を自由入力で指定
    Note: 指定された章のみ Edit で修正し、再度確認を依頼
  - C: ヒアリング再実施（全体再生成）
    description: 特定ラウンドからヒアリングをやり直す
    Note: 既存ドラフトは `requirements.md.regen.YYYYMMDDhhmm.bak` として退避
  - D: その他（自由入力）
    description: 上記以外の対応（章追加削除等）
    Note: 自由入力欄で要望を記載してください
```

修正指示があれば該当章を編集し、Step 5 を繰り返す（最大3回）。

### Step 6: コミット承認ゲート & コミット

1. 修正完了後、AskUserQuestionで最終承認を確認（コミット承認ゲート）：

```
質問: "requirements.md をコミット・プッシュしてよいですか？"
ヘッダー: "コミット承認ゲート"
選択肢:
  - A: 承認してコミット・プッシュ
    description: einja-task-commit Skillでコミット・プッシュを実行
    Note: ブランチへの反映が確定する。バックアップファイルも同コミットに含めるか別途確認
  - B: コミットは保留（手動でコミットする）
    description: 生成ファイルはディスクに残し、コミット操作はユーザーが実施
    Note: einja-task-commit を呼ばずに本Skillを終了
  - C: その他（自由入力）
    description: 追加修正 / 別ブランチへのコピー等
```

2. 承認時は `einja-task-commit` Skillを呼び出してコミット：
   - 新規作成（未存在から作成 / 最初から / 上書き）: `docs: プロジェクト要件定義書を追加`
   - 既存維持系（続きから / 手動指定）: `docs: プロジェクト要件定義書を更新`
   - バックアップファイル（`*.bak`）はコミットに含めるかユーザーに確認

## 既存ファイル処理（続きから / 手動指定モード詳細）

| 状況 | 対応 |
|------|------|
| §X が既存にあり、ユーザーが「変更不要」と回答 | 既存記述をそのまま保持 |
| §X が既存にあり、ユーザーが「変更あり」と回答 | 既存記述を基準に Edit で差分反映。版歴表（§16.3）に新版番号で追記 |
| §X が既存になく、新規追記 | テンプレートから新規生成して挿入 |
| 既存に承認欄（§16.2）の記載あり | 削除せず保持し、新版分の承認欄を追加 |

**バックアップ規約**:
- Step 0 で「最初から」（選択B）を選んだ場合は `requirements.md.start-over.YYYYMMDDhhmm.bak` を生成（タイムスタンプは `date +%Y%m%d%H%M`）
- Step 0 で「上書き」（選択C）を選んだ場合は `requirements.md.overwrite.YYYYMMDDhhmm.bak` を生成
- Step 5 で「全体再生成」（選択C）を選んだ場合は `requirements.md.regen.YYYYMMDDhhmm.bak` を生成（複数回再生成での衝突回避のためタイムスタンプを必ず付与）
- 「続きから」（選択A）/「手動指定」（選択D）はバックアップを生成しない（既存ファイルを Edit で更新する運用）
- `requirements.md.bak` という接尾辞は**現バージョンのSkillでは生成しない**。旧仕様の差分追記モードで生成されていた接尾辞であり、`.start-over.*.bak` / `.overwrite.*.bak` / `.regen.*.bak` と命名衝突しないようリザーブする
- 各バックアップ命名は接尾辞で衝突しないこと（`.start-over.YYYYMMDDhhmm.bak` / `.overwrite.YYYYMMDDhhmm.bak` / `.regen.YYYYMMDDhhmm.bak` の3種類）
- バックアップは `.gitignore` 推奨だが、コミット時にユーザー判断で含めることも可

## 連携

- **呼び出し元**: ユーザー（手動 `/einja-project-requirements` または description トリガーによる自然発火）
- **依存Skill**:
  - `_einja-subagent-question-protocol` - サブエージェント質問プロトコル（事前調査で起動する general-purpose / Explore に適用）
  - `_einja-output-format` - 統一出力フォーマット
  - `einja-task-commit` - 承認後のコミット・プッシュ
- **委任先（任意）**: 事前調査時に `general-purpose` / `Explore` サブエージェントを並列起動可（最大3並列）
- **連携可能Skill（オプション）**: `einja-review-spec` でドラフトのレビュー実施可能（ユーザー希望時）

## エラー処理

| エラー種別 | 原因 | 対処 |
|-----------|------|------|
| `docs/project/` 作成失敗 | パーミッション不足 / worktree未設定 | エラーメッセージを表示し、ユーザーに作業ディレクトリ確認を依頼 |
| 既存ファイル読み込み失敗 | ファイル破損・エンコーディング問題 | バックアップ作成後、新規作成モードへフォールバック（ユーザー確認） |
| AskUserQuestionで全選択肢が「その他」 | ユーザーが想定外回答を希望 | 自由入力を解釈し、最も近い動作にマッピング。曖昧なら再質問 |
| サブエージェントが PENDING_QUESTIONS を返却 | 事前調査中に判断必須事項を検出 | `_einja-subagent-question-protocol` に従い、調査可能な質問は自律解決、判断必須は AskUserQuestion でユーザーへエスカレーション |

## 実行制約

- 本Skillは親エージェント（オーケストレーター）として動作する
- AskUserQuestion / Read / Write / Edit / Bash / Grep / Glob / Task / Skill ツールを使用
- `context: fork` は設定しない（ユーザー対話 + 内部Skill/Agent呼び出しのため、親コンテキストで動作）
- ファイル生成は `docs/project/` 配下のみ（マネージドディレクトリ `docs/einja/` には書き込まない）

### ユーザー中断時の共通ハンドリング

ユーザーが任意の AskUserQuestion で cancel / 中断系の自由入力を行った場合は、以下を共通ハンドリングとして適用する:

- 中断時点までの Edit はディスクに残存する（ロールバックしない）
- 再開時は Step 0.1 のパース推定で続きから自動再開可能
- 中断したことをユーザーにアナウンスし、`einja-task-commit` の手動実行を推奨する
