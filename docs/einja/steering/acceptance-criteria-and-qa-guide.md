# 価値あるテストを生む要件定義とテスト設計ガイド

## 1. 受け入れ基準の原則

### Do
- 振る舞い・入力・観測可能な結果をセットで書く（Given/When/Then または 条件/操作/期待結果）。
- ビジネス価値やユーザー影響が分かる文脈を添える（誰が何のために使うか）。
- 正常系に加え、代表的な異常・境界ケースを列挙する。
- 観測手段（API レスポンス、イベント、DB 状態など）を明示する。
- 実装と無関係な用語で書き、内部構造への言及は避ける。

### Don't
- 「ファイルが存在する」「〇〇を返すクラスがある」など構造・命名のみを確認させる。
- 単一の肯定文で完結させて振る舞いの条件や観測結果を書かない。
- テストレベルを曖昧にし、誰がどの観点で検証するか不明瞭にする。
- 期待結果を「問題ないこと」「成功すること」で済ませる。
- 実装手段（特定フレームワーク、DB テーブル構造など）を強制する。

### 完了レベル（readiness level）を混在させない

AC や完了条件は、対象（特に backend / API / DB / auth / 外部連携 / インフラを伴うコンポーネント）の「どこまで到達すれば完了か」を **1 つの readiness level に固定**して書く。`created`（箱が作られた）と `healthy`（外部依存込みで実際に動く）を同一 AC に混ぜると、「箱は作れたが外部依存が無くて healthy にできない」段階が曖昧になり、順序事故・完了誤認を招く。

#### readiness level の定義（5 段階）

| level | 意味 | 完了確認の例 |
|-------|------|-------------|
| `created`（materialized） | リソース・ファイル・コンポーネントの実体が存在する | ファイル / レコード / サービス / テーブルが存在する |
| `configured` | 設定値・env・接続文字列・権限が投入された（まだ外部疎通はしない） | 設定が読み込まれ、エラーなく起動可能な状態 |
| `external-deps-ready` | 依存する外部リソース（DB / secret / DNS / OAuth / 外部 API）が揃い接続可能 | DB migrate 済 + 接続文字列が有効、secret 注入済、DNS 解決可 |
| `healthy` | 外部依存込みで稼働し、health check / 主要動作が通る | `/health` が 200、代表的な read / write が成功 |
| `E2E-ready` | ユーザー導線・他コンポーネント連携を含め、E2E シナリオが通せる | 主要シナリオが端から端まで通る |

#### 規約

- 1 つの AC / 完了条件で確認する readiness level は **1 段階に固定**する。`created` を確認する AC と `healthy` を確認する AC は分ける。
- `healthy` 以上を完了条件にする AC は、**前提となる external-deps を明記**する（例: 「API が healthy ← DB migrated + connection string injected」）。external-deps が未充足の段階で `healthy` の AC を「完了」と判定しない。
- インフラ・サービス・外部連携を含む機能では、コンポーネントごとの到達レベルを **readiness matrix**（`docs/einja/templates/readiness-matrix.md.template`）で俯瞰し、各 AC がどの level を担保するかを対応付ける。
- まだ到達できない level は `blocked-by`（何待ちか）/ `deferred-to`（どのタスク・Phase で到達するか）を明示し、未到達を「失敗」ではなく「段階」として扱う。

#### 最終受け入れの readiness 下限（"できたつもり"完了の禁止）

上記の規約が「1 つの AC 内で level を混在させない」という**粒度**を定めるのに対し、ここでは「Issue / 機能の**最終受け入れ**がどの level に到達して初めて"完了"と呼べるか」という**到達下限**を定める。成果物が `created` / `configured` 止まり（箱は作ったが価値が届いていない＝"できたつもり"）の状態を「完了」と判定してはならない。

1. **デフォルト（ユーザー導線がある変更）**: 最終受け入れの AC 群には `E2E-ready`（ユーザーと同等の操作で価値が端から端まで届く）を担保する AC を**1 件以上**含める。`created` / `configured` を確認する AC の集合だけで「完了」としない。
2. **ユーザー導線が無い変更（インフラ / ライブラリ等）**: `E2E-ready` は免除してよいが、**検証ゼロは不可**。変更後に対象が `healthy`（外部依存込みで疎通・主要動作が通る）ことを確認する AC を必ず置く。`E2E-ready` を免除する場合は readiness matrix に **N/A の理由を明記**する（理由なき N/A は不可）。
   > **「ユーザー導線が無い」の判定基準**: エンドユーザー（人間）が UI / API 操作を経由して価値を受け取るパスを一切含まない変更のみ免除対象とする（例: CI/CD 設定変更、依存ライブラリ更新、運用者向けでないバックグラウンド定期ジョブ）。Webhook 受信・管理 API・管理画面など「操作者がいる」変更は原則「ユーザー導線あり」とみなし `E2E-ready` を求める。判定に迷う場合は導線ありに倒す。
3. **マージ後 / デプロイ後にしか本質的に確認できない場合**: 次の両方を必須とする。
   - (a) 後続フェーズ / 工程への**申し送り事項**: readiness matrix の `deferred-to` 列に「どの工程で `healthy` / `E2E-ready` に到達させるか」を記載する。
   - (b) **人間 QA テスト手順**: `qa-test.md` のシナリオ一覧に**種別 `人手E2E`** のシナリオを用意し、マージ / デプロイ後に人手で実行する手順（テスト手順テーブル）を記述する。
4. **N/A は「本当に確認が不可能な場合のみ」**。「面倒」「時間が無い」等は N/A の理由にならない。

> **種別 `人手E2E` の記法**: `qa-test.md` の「シナリオ一覧」テーブルの `種別` 列に `人手E2E` を用いる。これは AI / 自動テストでは検証しきれず、マージ / デプロイ後に人間が実環境で端から端まで操作して価値到達を確認するシナリオを指す。手順は「テスト手順」テーブル（No / 手順 / 確認項目 / 期待値 / 結果 / 備考）に具体的なユーザー操作として記述する。

> **責務境界**: 本規約は「最終受け入れの到達下限を**仕様・レビュー時点で担保させる**入口ゲート」である。デプロイ環境で AC を実際に実行する**実行・QA層**の責務（phase-reviewer / task-qa）とは補完関係であり、本規約は実行そのものには踏み込まない。

### 振る舞い駆動テンプレート

> **Note**: AC IDの直後に記載する「振る舞いの名前」は、この受け入れ基準の内容を1文で要約したものです。Given/When/Thenの詳細を読まなくても概要が把握できるようにしてください。

> **AC ID形式**: `AC{Story#}.{CAT}.{N|E}.{連番3桁}`（Story#=ユーザーストーリー番号、CAT=カテゴリ、N=正常系/E=異常系、連番はStory×カテゴリ×区分ごとに001から採番）。カテゴリは「ACカテゴリの推奨定義」セクションを参照。

```
AC1.CAT.N.001: <振る舞いの1文要約>
- 前提: <状態/入力/役割>
- 操作: <ユーザー操作 or システムイベント>
- 期待結果: <観測可能なアウトプット>（例: HTTP ステータス/レスポンス/DB 変化/イベント）
- 検証レベル: <Unit | Integration | E2E | Browser>（複数可）
- 補足: <ビジネスルールやエッジケース>
```

> **Markdown形式（requirements.mdで使用）**: 上記テンプレートをrequirements.mdに記載する場合は、以下のチェックボックス付きインデント形式を使用してください：
> ```
> - [ ] **AC1.CAT.N.001**: <振る舞いの1文要約>
>   - Given: <前提条件>
>   - When: <操作>
>   - Then: <期待結果>
>   - 検証レベル: <Unit | Integration | E2E | Browser>
> ```

### ユーザーストーリー起点の構造

ACは**ユーザーストーリー（Story）単位で整理**する。requirements.md の §4 配下に、Story番号ごとのサブセクションとしてACを記述する。

#### Story単位でACを整理する理由

- **誰の・何のためのACか**が明確になる（Story IDが常に文脈を示す）
- 長大スクロールを回避し、StoryごとにACの粒度・数が適切か確認しやすい
- QAシナリオと要件書のACを `AC{Story#}.*` プレフィックスで即座に対応付けられる

#### AC命名体系

```
AC{Story#}.{CAT}.{N|E}.{連番3桁}
```

| 部位 | 意味 | 例 |
|------|------|-----|
| `Story#` | ユーザーストーリー番号（1始まり） | `1`, `2`, `3` |
| `CAT` | カテゴリ（UI/NAV/VAL/ERR/PERM/UX等） | `UI`, `VAL`, `ERR` |
| `N\|E` | 正常系（N）/ 異常系（E） | `N`, `E` |
| `連番3桁` | Story × カテゴリ × 区分ごとに `001` から採番 | `001`, `002` |

**採番ロジック**: Story番号・カテゴリ・区分（N/E）の組み合わせが変わるたびに001からリセットして採番する。  
例: `AC1.UI.N.001`, `AC1.UI.N.002`, `AC1.UI.E.001`, `AC2.UI.N.001`

```markdown

#### Story数が多い場合の目次運用

Story数が5以上になる場合は、§4の冒頭に目次を設ける。Story番号で各Storyにクイックジャンプできるようにすると、レビュアーとQAエンジニアの双方が参照しやすい。

```markdown
## 4. 受け入れ基準

### 目次
- [Story 1: ユーザー登録](#story-1)
- [Story 2: ログイン](#story-2)
- [Story 3: パスワードリセット](#story-3)
```

#### カテゴリ別横断参照

特定カテゴリ（例: すべてのERR系AC）を横断的に確認したい場合は、AC一覧（俯瞰テーブル）の `カテゴリ` 列でフィルタする。Story × カテゴリ の交差テーブルを補助資料として用意すると、観点漏れの発見が容易になる。

#### qa-test.md.template との整合

`docs/einja/templates/qa-test.md.template` は本AC命名体系と完全整合している。QAテスト仕様書の「関連AC」欄は必ず `AC{Story#}.{CAT}.{N|E}.{連番3桁}` 形式で記述すること。ハイフン区切りの旧形式は使用しない。

#### AC詳細のシーン主軸構成

requirements.md §4 の AC詳細は、AC を **シーン（画面の状態・操作局面）単位の見出し** で並べる。カテゴリ別（UI/VAL/…）に分けるのではなく、1つのシーン見出しの下にそのシーンで関わる各カテゴリのACを混在で並べることで、1つの業務的振る舞い（例: 保存フロー）に関わるACが1か所に集まり、レビュー時の観点漏れを発見しやすくする。

- **シーン語彙は固定enumにしない**。画面の性質に応じて増減してよい。フォーム画面の推奨ベースライン: `初期表示 / 入力中 / 送信時 / 送信成功時 / 送信失敗時`。一覧・ウィザード・ダッシュボード・バッチ・API単体などは異なるシーン構成を取ってよい
- 該当ACの無いシーンは **空の見出しを作らず省略** する
- **「画面横断」見出しは常設** し、特定シーンに属さない横断的AC（権限PERM・性能・セキュリティ等）の受け皿とする（横断ACのオーファン化を防ぐ）
- **シーン↔カテゴリの配置**: 同一シーン見出しの下に UI/NAV/VAL/ERR/UX 等の複数カテゴリのACを混在配置してよい（例: 「送信時」シーンに VAL系と UX系を併置）。特定シーンに属さない PERM・性能・SEC は「画面横断」に置く
- **UX系ACの配置**: 送信中ローディング・送信時フォーカス移動など **特定シーンに紐づくUX** は、そのシーン（「送信時」等）に置く。画面全体に効く操作性（キーボードナビゲーション・全体的アクセシビリティ等）のみ「画面横断」に置く
- AC-ID は従来どおり `AC{Story#}.{カテゴリ}.{N|E}.{連番3桁}`。**シーンは見出しにのみ用い、AC-ID には含めない**。カテゴリは AC-ID と AC一覧表の「カテゴリ」列の両方に残す（QA のテスト種別判定がカテゴリ列に依存するため）

## 2. テスト設計の原則

### テストレベルと責務
- **単体 (Unit)**: 単一モジュールの意思決定ロジックを高速に検証。外部依存はモック化し、条件分岐とエッジケース網羅。
- **統合 (Integration)**: 境界（Repository+DB, UseCase+Gateway, API+Middleware など）越しの契約を検証。実際のインフラ接続や本物に近いセットアップを使い、主要なハッピーパス＋代表的な異常系を確認。
- **E2E**: Playwrightコードによる自動テスト。`pnpm test:e2e`で実行され、リグレッション防止に使用。
- **Browser**: Playwright MCPによるブラウザテスト。task-qa Skillで実行され、画面フロー・UIインタラクションの確認に使用。

> **Note**: E2EはPlaywrightコードによる自動テスト（`pnpm test:e2e`で実行）、BrowserはPlaywright MCPによるブラウザテスト（task-qa Skillで実行）です。

### 価値あるテスト判定基準
- 仮説: テストが守るべきビジネスルールや SLA が明文化されている。
- 分離: 振る舞い単位の原因→結果を説明できる。
- 再現性: 決定論的で、入力と期待結果から誰でも同じ結論を得られる。
- 監視性: 失敗時に「何が壊れたか」がメッセージやログから分かる。
- 保守性: 実装ディテールではなく契約・振る舞いに結び付いているため、内部構造変更で安易に壊れない。
- コスト対価: 実行時間/セットアップコストに見合うリスク低減効果がある。

### 推奨項目構造

要件書とQA仕様書を「AC本文だけ」で終わらせず、先に一覧化・分類すると、レビューとテスト設計の速度が上がる。今後は以下の項目構造を推奨する。

#### 要件書の推奨構造

- `Sources`: Asana / Figma / 実装 / 関連spec / QA結果
- `目的・役割`: 対象ユーザー、主要ユースケース、対象外
- `前提条件・制約`: ロール、データ前提、ファイル制約、業務制約
- `画面構成・状態`: レイアウト構成、状態パターン
- `AC一覧`: AC を俯瞰する表
- `AC詳細`: 正常系 / 異常系に分離した Given/When/Then
- `ルール系セクション`: 表示・計算、入力、権限、遷移、処理フロー

#### QA仕様書の推奨構造

- `概要`: ページ / 機能、関連spec、対象ロール
- `テスト環境`: URL、テストデータ、ログイン条件
- `AC一覧`: AC とシナリオの対応表
- `シナリオ一覧`: シナリオの俯瞰表
- `シナリオ詳細`: 目的、関連AC、前提条件、手順、結果

### AC一覧の推奨列

| 列 | 目的 |
|----|------|
| `AC ID` | 一意識別 |
| `カテゴリ` | `UI / NAV / VAL / ERR / PERM / UX` など観点分類 |
| `区分` | 正常系 / 異常系 |
| `一文サマリ` | 内容を一目で把握する |
| `強度` | `MUST / SHOULD / MAY` を明示する |
| `検証レベル` または `カバーシナリオ` | テスト責務またはQA対応関係を明示する |

### ACカテゴリの推奨定義

- `UI`: 初期表示、要素表示、表示条件、状態表示
- `NAV`: 保存後遷移、キャンセル、モーダル遷移、画面離脱
- `VAL`: 必須、形式、範囲、相関チェック
- `ERR`: 取得失敗、保存失敗、再試行、エラー表示
- `PERM`: 閲覧可否、編集可否、API実行可否
- `UX`: 多重送信防止、ローディング、警告表示、補助メッセージ、4状態実装（disabled/error/empty/loading）、フォーカス管理（初期フォーカス・エラー時フォーカス移動・モーダルトラップ）、操作後フィードバック（成功/失敗の確認表示）
  ※ ERRカテゴリ（エラーの発生・表示・再試行）と重複する場合あり。ERRは機能面、UXは体験品質面から確認する。

### AC記述の粒度

- AC本文は振る舞いの骨格を書く
- 詳細条件、計算式、入力制約、権限差分、遷移条件は後続セクションへ委譲する
- AC本文では `→ §N 入力ルール` のように参照を張る
- AC詳細は `正常系` と `異常系` を分ける

#### 粒度の判定基準（唯一のルール）

ACを分けるか統合するかは **「観測可能な結果（Then）が異なるか？」だけ** で決める。入力フィールドの数・バリデーション種別の数でACを増やしてはならない。

##### DO
- 1つの観測可能な結果 = 1つのAC（振る舞いの骨格のみ記述）
- 形式・桁数・正規表現・必須等のフィールド別詳細は §6 入力ルール表へ委譲し、AC本文は `（→§6 VR-{Story#}-{連番3桁}）`（例: `VR-1-001`）で参照を張る
- 例: 「必須未入力でも形式不正でも → 同じ『送信が阻止されエラー表示される』」なら **AC は1本**。個別の条件・文言差は §6.2 の複数行（VR-ID）で表現する

##### DON'T（頻出アンチパターン3種）
- ✗ フィールドごとにAC: `AC1.VAL.E.001 メール必須` / `AC1.VAL.E.002 氏名必須` …（観測結果が同じなら1本に統合し §6.2 に行を足す）
- ✗ バリデーション規則ごとにAC: 「空欄エラー」「形式エラー」「桁数エラー」を別AC（→ 1ACに統合、§6.2 にVR 3行）
- ✗ AC本文にバリデーション詳細を直書き（「RFC5322準拠で…」→ §6.2 へ移動し VR参照に置換）

##### §4 ↔ §6 の役割分担（SSoT）
| 所有者 | 内容 |
|--------|------|
| §4 AC | 振る舞いの骨格（誰が・何をすると・どんな観測可能な結果になるか）＋ `→§6 VR-ID` 参照 |
| §6.2 入力ルール表 | フィールド別の 必須 / 形式 / 範囲 / タイミング / **エラーメッセージ文言**（文言のSSoTは §6.2） |

**VR-ID命名規則**: §6.2 入力ルール表の各行に `VR-{Story#}-{連番3桁}`（例: `VR-1-001`、連番はStoryごと001から）を付与する。AC本文（§4）からは `（→§6 VR-1-001）` の形式で参照する。
- 複数のVR行を参照する場合は **カンマ区切りで全VR-IDを列挙** する（例: `（→§6 VR-1-001, VR-1-002, VR-1-003）`）。範囲記法（`VR-1-001〜VR-1-006` の `〜`）は使わない（§4↔§6.2 の双方向整合を機械的に突合できるようにするため）。
- **AC一覧表の参照列の簡潔化**: AC一覧表（俯瞰用）の「参照」列はフィールド数が多いと冗長になるため、`§6.2`（または代表VR-ID）に簡潔化してよい。**双方向整合の正本は AC詳細本文の `（→§6 VR-1-001, VR-1-002, …）` 全列挙**とし、レビューの双方向チェックはAC本文の列挙を基準に行う。
- **§6.2 の行粒度**: 1フィールドに **エラーメッセージが分かれる複数規則** がある場合は、規則ごとにVR行を分ける（例: 画像のサイズ超過と形式不正でメッセージが異なるなら2行）。メッセージが1本に統合できる場合のみ1行にまとめてよい。これにより「フィールド数による水増し」を §6.2 へ転嫁しない。

##### 生成後セルフチェック（requirements 作成時に必ず実行）
- [ ] 同一Story内に Then がほぼ同文の VAL系AC が2本以上ないか → あれば統合し §6.2 に行を追加
- [ ] AC本文に正規表現・桁数・形式詳細が直書きされていないか → §6.2 へ移し VR参照に置換
- [ ] §6.2 の各行に VR-ID が付与され、対応する §4 AC の「参照」列から引かれているか
- [ ] エラーメッセージ文言が §6.2 のみに存在し §4 に重複していないか
- [ ] ユーザー導線がある変更の場合、最終受け入れACのうち1件以上が **E2E-ready**（ユーザーと同等の操作で価値が端から端まで届く）を担保しているか（→ 「最終受け入れの readiness 下限」節）

### QAシナリオ設計の必須項目

各シナリオには最低限以下を持たせる。

- `目的`
- `関連AC`
- `前提条件`
- `テスト手順`
- `結果`

`前提条件` は以下の3項目を標準とする。

- `テストデータ`
- `ログインロール`
- `依存`

`テスト手順` の表は以下の列を標準とする。

| 列 | 目的 |
|----|------|
| `No` | 手順番号 |
| `手順` | 実施操作 |
| `確認項目` | 何を確認するか |
| `期待値` | 観測可能な期待結果 |
| `結果` | 実施後に記録 |
| `備考` | 関連ACや補足 |

### テスト-ファースト原則（ATDD）
テスト設計は**実装前**に行う。ワークフローは以下の順序で実行する：

```
要件定義 → 設計 → QAテスト仕様（シナリオテスト含む）→ タスク分割 → 実装 → QA（実行のみ）
```

**禁止事項**:
- 実装後にテスト設計を行うこと
- テスト仕様なしでタスク分割を行うこと
- QAフェーズでテスト設計を新規作成すること（既存仕様の確認・実行のみ）

### シナリオテスト
シナリオテストは、複数のタスクをまたいで継続的に実行される操作フローを検証する。

**シナリオテストの目的**:
- 個別タスクのテストでは検出できない統合問題を発見
- ユーザーが実際に行う操作フロー全体の動作を確認
- タスク間の依存関係と連携を検証

**シナリオテストの特徴**:
- 複数のタスクグループにまたがる
- 各タスク完了時に実施可能な範囲が拡大
- Issue全体で共有される（`qa-tests/scenarios.md`に記載）

**シナリオテストテンプレート**:
```markdown
## シナリオ#1: [シナリオ名]

### 目的
[このシナリオで確認したいこと]

### 関連
- **受け入れ条件**: AC1.UI.N.001, AC1.NAV.N.001, AC1.ERR.E.001（シナリオに関連するAC ID）

### 実施タイミング
- **AC1.UI.N.001〜AC1.UI.N.003実装後**: Step 1-3まで実施可能
- **AC1.NAV.N.001〜AC1.NAV.N.002実装後**: Step 1-5まで実施可能
- **AC1.ERR.E.001実装後**: 全Step実施（フルシナリオ）

### テスト手順

| Step | 操作 | 確認項目 | 期待値 | 結果 |
|------|------|---------|--------|------|
| 1 | [操作内容] | [確認する項目] | [期待される結果] | - |
| 2 | ... | ... | ... | - |

### 実行ログ
（実施後に記載）
```

**シナリオテストの設計タイミング**:
- `einja-issue-spec-create` Skill の QAテスト仕様生成フェーズで作成
- requirements.md の受け入れ条件を分析し、複数ACをまたぐフローを特定
- タスク分割前に完了させる

## 3. 具体例集

### ケース1: データベース層（Repository）
- 悪い例: 「UserRepository が実装されている」
- 良い例:
  ```
  AC1.VAL.E.001: UserRepository はメールアドレス重複を防ぐ
  - 前提: 同一メールを持つユーザーが既に存在
  - 操作: create({email}) を呼ぶ
  - 期待結果: Result.Err(DuplicateEmail) を返し、DB 状態は変化しない
  - 検証レベル: Integration（実 DB or Testcontainer）
  ```

### ケース2: アプリケーション層（UseCase）
- 悪い例: 「UseCase がオブジェクトリテラル形式で定義されている」
- 良い例:
  ```
  AC2.UI.N.001: PasswordResetUseCase はトークン発行後にメール送信イベントを発火
  - 前提: 対象ユーザーが存在し、メール送信サービスが利用可
  - 操作: execute({userId})
  - 期待結果:
      1. TokenRepository に 1 件レコード生成
      2. DomainEventBus へ PasswordResetRequested を publish
  - 検証レベル: Unit（メール送信はモック）、Integration（イベントバス接続）
  ```

### ケース3: API 層（REST）
- 悪い例: 「API エンドポイントが定義されている」
- 良い例:
  ```
  AC1.PERM.E.001: GET /users/:id は権限エラーを 403 で返す
  - 前提: 認証済みユーザー A がユーザー B を参照しようとする
  - 操作: GET /users/B
  - 期待結果: HTTP 403, body {"code":"FORBIDDEN","message":"..."}
  - 検証レベル: Integration（API + DB + 認可ミドルウェア）
  ```

### ケース4: バッチ処理（Cron）
- 悪い例: 「job:cleanup スクリプトが存在する」
- 良い例:
  ```
  AC1.UI.N.001: cleanup ジョブは 30 日以上未使用のセッションを削除
  - 前提: session テーブルに 29 日/30 日/31 日経過データが混在
  - 操作: job:cleanup を実行
  - 期待結果: 31 日 > のレコードのみ削除、削除件数をログ出力
  - 検証レベル: Integration（実 DB）、E2E（ステージングで日次 Cron 監視）
  ```

### ケース5: フロントエンド（画面）
- 悪い例: 「ログイン画面コンポーネントが存在する」
- 良い例:
  ```
  AC1.ERR.E.001: ログインフォームは誤ったパスワードで API エラーを表示
  - 前提: ユーザーが存在、間違った PW を入力
  - 操作: Submit
  - 期待結果:
      1. /api/login が 401 を返すまでスピナー表示
      2. フォーム上に "メールアドレスまたはパスワードが違います" を表示
  - 検証レベル: Unit（フォームバリデーション）、E2E（Playwright で API モック無）
  ```

### ケース6: UX（ユーザビリティ）

AC記述例（AIが Playwright MCPで自律検証可能なもの）:

- **悪い例**: 「フォームに送信ボタンがある」
- **良い例**:

  AC1.UX.N.001: 保存ボタンはAPI送信中にdisabledになり多重送信を防ぐ
  - 前提: フォームに有効な入力値が入力済み
  - 操作: 保存ボタンをクリック（APIレスポンス待ち中）
  - 期待結果: ボタンがdisabled状態でローディングスピナーを表示。APIレスポンス後にenabled状態に戻る
  - 検証レベル: Browser

  AC1.UX.E.001: 必須フィールド未入力時にフィールド直下にエラーメッセージが表示される
  - 前提: 必須フィールドが空
  - 操作: 保存ボタンをクリック
  - 期待結果: 該当フィールドがerror状態になり、フィールド直下にエラーメッセージを表示。フォーカスが最初のエラーフィールドへ移動
  - 検証レベル: Browser

  AC1.UX.N.002: データが0件の場合にempty stateメッセージを表示する
  - 前提: データが0件
  - 操作: 一覧画面を表示
  - 期待結果: テーブル非表示、「データがありません」等のempty stateを表示
  - 検証レベル: Browser

### エージェント指示
- **task-executer**
  - AC で指定された振る舞いをテストで再現しているか確認。
  - 期待結果を実装ではなく外部契約（レスポンス、イベント、DB 状態）に結び付ける。
  - 「構造だけを確認するテスト」は reject（例: `expect(fileExists).toBe(true)` など）。
- **task-qa**（🔴 ATDD準拠・動作確認必須）
  - **Phase 1-2: テスト設計**
    - AC に対応する Given/When/Then 形式のテストシナリオを設計。
    - 構造確認だけのテストは設計禁止（「ファイルが存在する」「ビルドが成功する」等）。
  - **Phase 3: 動作確認実施（🔴 最重要・必須）**
    - 画面修正 → **ブラウザテスト（Playwright MCP）** で `browser_navigate` → `browser_snapshot` → 操作 → 結果確認
    - API修正 → **API打鍵テスト（curl）** で `curl -i` リクエスト送信・レスポンス確認
    - **ビルド/Lint成功だけでSUCCESSと判定することは禁止**
    - **動作確認を実施せずにSUCCESSと判定することは禁止**
    - 動作確認の実行ログを報告に必ず含める
    - **外部API連携機能で、環境変数未設定のまま「テストPASS」を根拠にSUCCESSにすることは禁止**
    - **モックテストのPASSは「動作確認」に該当しない。実APIとの通信確認が必須**
    - 環境変数未設定で動作確認不可の場合は **FAILURE（failureCategory=D: 環境問題）** として報告
  - **Phase 4: 自動テスト**
    - pnpm test, lint, build, typecheck を実行
  - **Phase 5: 結果報告**
    - 「Phase 3: 動作確認実施記録」セクションが空の場合、SUCCESSは認められない
    - AC ごとの検証結果と検証方法を明記

## 6. QAテストの責務分離

### 単体テスト vs QAテスト

| 観点 | 単体テスト (Unit) | QAテスト (Integration/E2E) |
|-----|------------------|---------------------------|
| **担当者** | task-executer（開発者） | task-qa（QAエンジニア） |
| **ツール** | Jest/Vitest | ブラウザテスト（Playwright MCP）、API打鍵テスト（curl） |
| **対象** | コンポーネント、関数、Hook等の個別動作 | 画面フロー、API連携、データ永続化等の統合動作 |
| **モック** | 外部依存はモック化 | 実際のインフラ接続 |
| **目的** | 単一モジュールの意思決定ロジック検証 | ユーザー視点での最終価値確認 |

**重要**: QAテストは単体テストではカバーできない**統合確認**を行うことが目的です。

## 7. QA実行フロー（5 Phase）

```
Phase 1: 事前確認
  ├── シナリオテスト仕様（scenarios.md）の確認
  ├── 必須自動テストの実行（pnpm test/lint/build/typecheck）
  └── すべて成功 → Phase 2へ / 失敗 → 即座にFAILURE

Phase 2: 実装整合性チェック
  ├── requirements.md の AC と実装の対応確認
  ├── design.md の設計と実装の整合性確認
  └── 不整合発見 → 差し戻し判断

Phase 3: 動作確認実施（🔴 最重要・必須）
  ├── 画面修正 → Playwright MCP で操作・確認
  ├── API修正 → Curl でリクエスト・レスポンス確認
  └── 動作確認なしでのSUCCESS判定は禁止

Phase 4: シナリオテスト実行
  ├── scenarios.md の該当シナリオを実行
  └── 複数タスクをまたぐフローの統合確認

Phase 5: 結果報告
  ├── qa-tests/ に結果を記録
  ├── 失敗時は原因分類（A/B/C/D）
  └── 次アクション決定（finisher/executer/qa-retry）
```

**Phase 2 補足（実装整合性チェック）**:
- **双方向チェック**: 「AC→実装」（ACが実装されているか）に加え、「実装→AC」（AC無しで実装された振る舞いが無いか）を逆引きする。design.md のAPI/画面要素と requirements.md のAC一覧をクロスチェックし、対応ACの無い実装（オーファン）を検出したら **B:要件齟齬** として requirements.md へ AC を追記してから先へ進む

**禁止事項**:
- ビルド/Lint成功だけでSUCCESSと判定すること
- Phase 3（動作確認）を実施せずにSUCCESSと判定すること

## 8. 失敗原因分類（A/B/C/D）

QAテスト失敗時、以下の4分類のいずれかに分類し、適切な戻し先を決定します。

### 8.1 分類フローチャート

```
QAテスト失敗
    ↓
質問1: 実装コードに問題があるか？
  YES → 【A: 実装ミス】 → task-executer
  NO → 質問2へ
    ↓
質問2: requirements.md の受け入れ条件が不正確・不完全か？
  YES → 【B: 要件齟齬】 → requirements.md修正 → task-executer
  NO → 質問3へ
    ↓
質問3: design.md の設計・アーキテクチャに問題があるか？
  YES → 【C: 設計不備】 → design.md修正 → task-executer
  NO → 質問4へ
    ↓
質問4: 環境・インフラ・テストツールに問題があるか？
  YES → 【D: 環境問題】 → qa再実行
  NO → デフォルトで【A: 実装ミス】として扱う
```

### 8.2 各分類の定義

| 分類 | 定義 | 判定基準例 | 戻し先 |
|-----|------|----------|-------|
| **A: 実装ミス** | コードの論理エラー、バグ、実装漏れ | TypeScriptエラー、ランタイムエラー、ロジック不具合、単体テスト失敗 | task-executer |
| **B: 要件齟齬** | requirements.md の受け入れ条件が実際の要求と異なる | ACの期待結果が曖昧、ビジネスルール未記載、AC間の矛盾 | requirements.md修正 → task-executer |
| **C: 設計不備** | design.md のアーキテクチャ・設計方針に問題 | トランザクション設計不備、スキーマ設計ミス、インターフェース不備 | design.md修正 → task-executer |
| **D: 環境問題** | テスト環境、インフラ、ツールの問題 | DB接続エラー、Playwright接続失敗、タイムアウト、ポート競合 | qa再実行 |

### 8.3 判定の優先順位

複数の分類に該当する可能性がある場合：

1. **D（環境問題）**: エラーメッセージが明確に環境起因の場合は最優先
2. **B（要件齟齬）**: requirements.md の記載が不正確・不完全な場合
3. **C（設計不備）**: design.md のアーキテクチャに問題がある場合
4. **A（実装ミス）**: デフォルト（不明な場合は実装ミスとして扱う）

#### D（環境問題）判定の厳格化

- **D と判定してよいのは**、エラーメッセージが 接続拒否 / タイムアウト / ポート競合 / DB接続不可 / secret・環境変数の未注入 を **明示している場合のみ**。実装由来の例外（null参照・要素未描画・想定外ステータス等）を「環境のせい」として D に分類してはならない
- **再試行上限は2回**。同一操作を（必要に応じデータ・認証情報を変えて）再試行し、3回目も同じ環境症状が再現する場合は D を確定とせず **ブロッカーとして人手判断にエスカレーション** する（D→qa再実行 の無限ループを禁止）
- 他の独立したACが正常に PASS しているかを確認し、当該ACのみ失敗する場合は環境起因の可能性を下げて A〜C を再検討する

### 8.4 実践例

#### 例1: トークン検証エラー
```
症状: TypeError: Cannot read property 'token' of undefined
分析: 質問1 YES（nullチェック漏れ）
判定: A: 実装ミス → task-executer
```

#### 例2: バリデーションエラーメッセージ不一致
```
症状: requirements.md「400エラーを返す」、実装「422エラーを返す」
分析: 質問1 NO、質問2 YES（ステータスコードが不明確）
判定: B: 要件齟齬 → requirements.md修正 → task-executer
```

#### 例3: トランザクション未実装
```
症状: 競合状態で整合性が保証されない
分析: 質問1 NO、質問2 NO、質問3 YES（トランザクション設計欠如）
判定: C: 設計不備 → design.md修正 → task-executer
```

#### 例4: PostgreSQL接続エラー
```
症状: Error: connect ECONNREFUSED 127.0.0.1:5432
分析: 質問1-3 NO、質問4 YES（PostgreSQLコンテナ未起動）
判定: D: 環境問題 → qa再実行
```

### 8.5 強度（MUST/SHOULD/MAY）によるリリース可否ゲート

QA結果は AC の強度に応じてリリース可否を判定する。

| 強度 | FAIL/未実施時の扱い |
|------|---------------------|
| MUST | **リリース不可（ブロッカー）**。1件でもFAIL/未実施があればリリースしない |
| SHOULD | リリース可だが **改善チケット登録と申し送りを必須** とする |
| MAY | 記録のみ（リリースをブロックしない） |

## 9. 動作確認ツールの使用ガイド

### 9.1 ブラウザテスト（Playwright MCP）

**用途**: ブラウザ操作による画面フロー・UI動作の確認

**基本フロー**:
```
1. browser_navigate でURLに移動
2. browser_snapshot でページ状態を取得
3. browser_click / browser_type で操作
4. browser_snapshot で結果確認
5. 必要に応じてスクリーンショット保存
```

**使用例（ログインフォーム）**:
```
手順1: ログイン画面に移動 (http://localhost:3000/auth/login)
手順2: スナップショット取得 → メールアドレス入力欄が表示されることを確認
手順3: メールアドレス入力: test@example.com
手順4: パスワード入力: password123
手順5: 送信ボタンをクリック
手順6: スナップショット取得 → ダッシュボード画面に遷移していることを確認
```

### 9.2 API打鍵テスト（curl）

**用途**: HTTPリクエスト/レスポンスによるAPI動作の確認

**基本フロー**:
```bash
# GETリクエスト
curl -i http://localhost:3000/api/users

# POSTリクエスト（JSON）
curl -i -X POST http://localhost:3000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"test@example.com","password":"password123"}'

# 認証付きリクエスト
curl -i http://localhost:3000/api/protected \
  -H "Authorization: Bearer {token}"
```

**確認項目**:
- HTTPステータスコード（200, 400, 401, 403, 404, 500等）
- レスポンスボディの内容
- レスポンスヘッダー（Content-Type, Set-Cookie等）

### 9.3 テストシナリオ記述形式

QAテスト仕様書では、以下の表形式で手順を記述します：

| No | 手順 | 確認項目 | 期待値 | 結果 | 備考 |
|----|------|---------|--------|------|------|
| 1 | ログイン画面に移動 (http://localhost:3000/auth/login) | URLが正しい | /auth/login | - | - |
| 2 | スナップショット取得 | メールアドレス入力欄が表示される | input[data-testid="email-input"]が存在 | - | - |
| 3 | メールアドレス入力: test@example.com | - | - | - | - |
| 4 | 送信ボタンをクリック | ローディング表示される | スピナーアイコンが表示 | - | - |

**重要な原則**:
- 手順は自然言語で簡潔に記述
- mcp__playwright などのコマンドは記載しない
- 「-」は手順のみで確認項目がない場合に使用
