# シナリオマスター（SSOT）

## このファイルの役割

`qa-tests/scenarios.md` はアプリ全体のQAシナリオ定義のSSOT（Single Source of Truth）として機能する。

**主な用途**:
- `_einja-task-qa` Skill がステップ3で参照し、対象ACの「実施タイミング（フェーズ）」と「検証方法」を特定する
- `_einja-phase-review` Skill がフェーズ単位のテスト対象シナリオを絞り込む際に参照する
- 各シナリオが何フェーズで実施されるかを一元管理し、`qa-tests/phase{N}/` 配下の実行結果ファイルとの対応を明確にする

**`qa-tests/phase{N}/` との関係**:
- 本ファイル: 全体シナリオの「定義」（変更頻度低・仕様主導）
- `qa-tests/phase{N}/{task-group-id}.md`: タスクグループ単位の「実行結果」（実施の都度更新）

```
3. ...

```

## シナリオ一覧

### SCN-001: 認証フロー（サインアップ〜サインイン〜サインアウト）

- **phase**: 1
- **AC**: AC1.UI.N.001, AC1.NAV.N.001, AC1.PERM.N.001
- **前提条件**: アプリが起動済み、DBが初期化済み、未登録のメールアドレスを用意している
- **検証方法**: Playwright MCP

#### 実施手順

1. `/signup` にアクセスし、メールアドレス・パスワードを入力してアカウントを作成する
2. 登録完了後、自動的に `/dashboard`（またはトップページ）にリダイレクトされることを確認する
3. いったんサインアウトし、`/login` から同じ認証情報でサインインする
4. 認証済み状態で保護されたページ（例: `/settings`）にアクセスできることを確認する
5. 再度サインアウトし、保護されたページにアクセスすると `/login` にリダイレクトされることを確認する

#### 期待結果

- サインアップ後に認証済みセッションが確立され、ダッシュボードが表示される
- サインイン後に同じセッションが確立される
- サインアウト後は未認証扱いとなり、保護ページへのアクセスがリダイレクトされる

### SCN-002: リソースCRUD操作（作成・読み取り・更新・削除）

- **phase**: 2
- **AC**: AC2.UI.N.001, AC2.UI.N.002, AC2.UI.N.003, AC2.UI.N.004
- **前提条件**: 認証済みセッションが存在する、対象リソースの一覧ページが実装済み
- **検証方法**: Playwright MCP（画面操作） / curl（API直接検証）

#### 実施手順

1. リソース一覧ページを開き、「作成」ボタンから新規リソースを入力して保存する（Create）
2. 一覧に新規リソースが表示されることを確認し、詳細ページを開く（Read）
3. 詳細ページの「編集」から内容を変更して保存し、変更が反映されることを確認する（Update）
4. 「削除」を実行し、一覧から該当リソースが消えることを確認する（Delete）
5. curl で対応する REST API エンドポイント（`POST /api/resources`, `GET /api/resources/:id`, `PATCH /api/resources/:id`, `DELETE /api/resources/:id`）を直接叩き、レスポンスとHTTPステータスを確認する

#### 期待結果

- 作成: 201 Created、レスポンスボディにIDが含まれる、一覧に新規レコードが表示される
- 読み取り: 200 OK、正しいリソースデータが返却される
- 更新: 200 OK、変更後の値がDBおよび画面に反映される
- 削除: 204 No Content（または200）、一覧から該当レコードが消える

### SCN-003: エラーハンドリング（バリデーション・未認証・存在しないリソース）

- **phase**: 2, 3
- **AC**: AC2.VAL.E.001, AC3.ERR.E.001
- **前提条件**: アプリが起動済み、フォームバリデーションおよびエラーレスポンスが実装済み
- **検証方法**: Playwright MCP（画面バリデーション） / curl（API異常系）

#### 実施手順

1. 必須フィールドを空のまま送信し、バリデーションエラーメッセージが表示されることを確認する
2. 不正な形式の値（例: メールアドレス形式でない文字列）を入力して送信し、適切なエラーが表示されることを確認する
3. curl で未認証状態（Authorizationヘッダーなし）のまま保護されたAPIを叩き、401 Unauthorized が返ることを確認する
4. curl で存在しないIDを指定してGETリクエストを送り、404 Not Found が返ることを確認する
5. 画面上でサーバーエラーが発生した場合にユーザーフレンドリーなエラーメッセージが表示されることを確認する

#### 期待結果

- 必須フィールド空送信: フォーム上にフィールドごとのエラーメッセージが表示され、送信が阻止される
- 形式不正: 該当フィールドにインラインエラーが表示される
- 未認証API: HTTP 401 + エラーJSONが返却される
- 存在しないリソース: HTTP 404 + エラーJSONが返却される
- サーバーエラー: 画面にエラートースト・エラーページが表示され、白画面にならない
