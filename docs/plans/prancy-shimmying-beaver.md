# 要件ヒアリングプロセス強化

## Context

`einja-issue-spec-create` Skillと配下サブエージェント群で、要件不明点の確認プロセスが弱い。Issue新規作成時にrequirements-generatorへ直行し、サブエージェントはビジネス要件の不明点を「最終手段」扱いで後回しにしている。推測で要件を補完してしまうリスクがあり、手戻りコストが高い。

## 現状

- `SKILL.md` の `0.2 要件方針` が1行のみ。Phase 1前のヒアリングステップなし
- サブエージェント4つ全てで「ユーザーへの確認」が「優先順位3: 最終手段」
- PENDING_QUESTIONSプロトコル自体は十分に整備済み（変更不要）

## 変更内容

### A. `einja-issue-spec-create/SKILL.md`

#### A1. セクション0.2の強化（41-43行目を置換）
「推測で補完せず確認する」方針を明記。技術的事実は自力解決OK、ビジネス要件は必ず確認。

#### A2. Phase 0.3「要件ヒアリング」追加（0.2の直後、現0.3ワークツリー作成の前に挿入）

**挿入位置の理由**: ヒアリング結果で方針が大きく変わる場合にworktreeが無駄になるのを防ぐ。要件確認→worktree作成→作業開始の順が自然。

**結果、番号が繰り上がる**: 現0.3→0.4、現0.4→0.5

Phase 0.3は「事前調査」→「ヒアリング」の2ステップ構成。

##### 0.3.1 事前調査（サブエージェント並列起動）

**方針**: 親エージェントが直接Explore/general-purposeエージェントを並列起動する（専用investigatorエージェントは不要）。調査は**広く浅く**（何を聞くべきかを決めるための最小限の調査）。深掘りはrequirements-generatorのStep 0に委譲する。

**調査観点と委託先**:

| 調査観点 | 委託先 | 目的 |
|---------|--------|------|
| 関連Issue・既存仕様書 | Explore | 類似機能の過去実装・決定事項を把握 |
| 既存コードの概要 | Explore | 影響範囲の見当をつける |
| 過去類似Planの確認 | Explore | 同じ失敗を繰り返さない文脈取得 |
| 外部リソース（Asana/Figma URL） | general-purpose | デザイン・タスクの意図を事前把握 |
| 外部依存の有無 | general-purpose | 外部API連携があれば専門的な質問が必要 |

- コンテキストに応じて不要な観点はスキップ（例: Asana URL未提供なら外部リソース調査は不要）
- Explore 1-2個 + general-purpose 0-1個を並列起動（最大3個）

##### 0.3.2 要件ヒアリング

**新規Issue作成時**:
1. 事前調査結果と一次情報（指示文等）を統合し、明示済み/不明を分離
2. ヒアリング観点チェックリストで不明点を洗い出す（対象ユーザー、ビジネス目的、機能スコープ、優先度、既存機能との関係、エッジケース、非機能要件、外部連携、デザイン制約）
3. 1回目のAskUserQuestionで全不明点を一括提示。回答不十分な場合のみ追加確認（最大2回追加 = 合計3回）
4. **3回後も必須要件が不明な場合**: 残存不明点を明示した上で「続行/中止」をAskUserQuestionで確認
5. 要件ヒアリングサマリを構造化（確定事項 + ユーザー回答 + 事前調査結果の要約 + 未解決事項）

**既存Issue操作時**:
1. 事前調査で既存仕様書（requirements.md、design.md等）を把握済み
2. 追加・変更要件との差分を分析し、影響範囲を特定
3. 新規作成時と同じヒアリング観点チェックリストを差分に対して適用し、不明点をAskUserQuestionで確認
4. 既存仕様との整合性について確認が必要な点も提示
5. 差分サマリを作成

#### A3. Phase 1の追加指示にサマリ受け渡しを追記
requirements-generatorプロンプトに「要件ヒアリングサマリ」+「事前調査結果」をインライン埋め込みで渡す指示を追加。これによりrequirements-generatorのStep 0での重複調査が減り、より深い調査に集中できる。

### B. サブエージェント4ファイル共通（Step 0の再設計）

対象:
- `.claude/agents/einja/issue-specs/requirements-generator.md`
- `.claude/agents/einja/issue-specs/design-generator.md`
- `.claude/agents/einja/issue-specs/qa-generator.md`
- `.claude/agents/einja/issue-specs/tasks-generator.md`

**変更**: 3段階の優先順位 → タイプ別の分岐に再設計

```
■ 技術的な事実確認 → 自力調査で解決OK（手段1: コード調査、手段2: Web検索）
■ ビジネス要件・スコープ・優先度 → 推測禁止。即座にPENDING_QUESTIONSで停止
```

- 「推測禁止ルール」を太字で明記
- 判断基準の具体例テーブルを追加（技術的事実 vs ビジネス要件の区別）
- design-generatorには補足追加:「アーキテクチャ選定に影響するビジネス制約（コスト、スケール目標、規制要件等）はビジネス要件に分類する」
- 各ファイル固有の調査項目（ガイドライン読み込み、Serena MCP等）はそのまま保持
