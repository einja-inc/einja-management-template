# Issue仕様タスク検証 Skill

## 概要

このSkillは、生成されたタスク一覧のフォーマットを検証し、違反があればエラーレポートを生成します。

## 責務

- 生成されたタスクのフォーマット検証
- 違反検出時にエラーレポート（Markdown形式）を生成
- 差し戻し判定（SUCCESS / FAILURE + エラー詳細）

## 使用タイミング

- tasks-validator サブエージェントから呼び出される
- einja-issue-spec-create Skillのタスク検証フェーズで使用
- タスク生成直後に自動実行

## 入力

- `tasks_markdown`: 検証対象のタスク一覧（Markdown形式）
- `retry_count`: 現在のリトライ回数（0から開始）
- `max_retries`: 最大リトライ回数（デフォルト: 3）

## 出力

### 成功時
```markdown
## バリデーション結果: SUCCESS

タスク一覧のフォーマットは正しいです。
次のフェーズに進んでください。
```

### 失敗時
```markdown
## バリデーション結果: FAILURE

### エラー一覧

1. **タスク X.Y.Z** - [エラー種別]
   - 問題: [問題の説明]
   - 修正案: [具体的な修正方法]

2. **行 NN** - [エラー種別]
   - 問題: [問題の説明]
   - 修正案: [具体的な修正方法]

### リトライ情報
- 現在の試行回数: N
- 最大試行回数: 3
- 残り試行回数: M
```

## 検証項目

### 0. 構造前提チェック（最優先・即FAILURE）

**以下のパターンが検出された場合、他の検証を行わず即座にFAILUREを返却する。**

- [ ] `Task X-Y` または `Task X.Y.Z` 形式のID表記がないか → `fundamental_format_violation`
  - 検出パターン: `/Task\s+\d+[-\.]\d+/i`
  - 正しい形式: `  - X.Y.Z タスク名`（`Task` プレフィックスは禁止）
- [ ] メタデータキーが `**太字**` でない行がないか → `missing_bold_metadata`
  - 検出パターン: `/^\s{4}-\s+(要件|実装AC|依存関係|完了条件|対応設計|シナリオテスト):/`（`**` で囲まれていない）
  - 正しい形式: `    - **要件**: Story X`
- [ ] Phase/タスクグループ/タスクの3階層構造が存在するか → `missing_hierarchy`
  - `### Phase` 見出し、`- [ ] X.Y` タスクグループ、`  - X.Y.Z` タスクの3つが全て存在すること

### 1. 構造検証
- [ ] Phase番号が1から連番になっているか
- [ ] タスクグループIDが `X.Y` 形式か
- [ ] タスクIDが `X.Y.Z` 形式か

### 2. インデント検証
- [ ] タスクが2スペースインデントか
- [ ] サブタスク/メタデータが4スペースインデントか

### 3. メタデータ検証（タスク単位で必須）
- [ ] **要件**: Story X
- [ ] **実装AC**: AC番号（例: `AC1.UI.N.001, AC1.VAL.E.001`）または `なし（理由）`
- [ ] **依存関係**: なし / X.Y / Phase X完了
- [ ] **完了条件**: [条件]（ACX.UI.N.001等を満たす）
- [ ] **対応設計**: design.md「セクション名」
- [ ] **シナリオテスト**: なし（理由） / シナリオX

### 4. 依存関係検証
- [ ] 参照先のタスクグループが存在するか
- [ ] 循環依存がないか
- [ ] 依存関係の書式が正しいか（`X.Y完了` は不可）

### 5. ATDDチェック
- [ ] Phase数が2-3個以内か
- [ ] タスクグループが縦切り（フルスタック）になっているか

### 6. 横切り検出（最重要）

**タスクグループ名に以下の禁止ワードが含まれていないか確認**：

| 禁止ワード | 理由 |
|-----------|------|
| `Domain` | レイヤーごとの分割 |
| `Infra` / `Infrastructure` | レイヤーごとの分割 |
| `UseCase` / `Application` | レイヤーごとの分割 |
| `API` / `Presentation` | レイヤーごとの分割 |
| `UI` / `画面` / `フロントエンド` | レイヤー/画面ごとの分割 |
| `層` | レイヤーごとの分割 |
| `Repository` | クラスごとの分割 |
| `Validator` | クラスごとの分割 |
| `Entity` | クラスごとの分割 |
| `Mapper` | クラスごとの分割 |
| `一覧` / `詳細` / `編集` / `削除` (単体) | 画面ごとの分割 |

**例外**:
- 「ユーザー作成・編集・削除機能」のように複数をまとめた場合はOK
- 「Domain〜UIまでフルスタック」のようにサブタスク説明に含まれる場合はOK
- タスク名（X.Y.Z）に含まれる場合はOK（タスクグループ名のみチェック）

**検出ロジック**:
```
タスクグループ名（X.Y 名前）の「名前」部分に禁止ワードが含まれていたらエラー
```

### 7. 任意メタデータ検証

任意項目のため、記載がなければスキップする。記載されている場合のみ形式をチェックし、**形式違反はFAILURE扱い**とする。

- [ ] `実行サブエージェント` が記載されている場合、`[名前]` 形式で単一指定か（複数指定は検証項目8でエラー）
- [ ] `使用Skill` が記載されている場合、`[名前]` or `[steering:名前]` 形式か（複数指定時はカンマ区切り: `[名前1], [steering:名前2]`）
- [ ] `対応UIデザイン` が記載されている場合、`ui-design-url\.md(「[\w-]+」)+（https://www\.figma\.com/design/[^\)]+）` 形式か
- [ ] インデントが正しいか（タスクグループレベル: 2スペース、タスクレベル: 4スペース）

**検出ロジック**:
```
実行サブエージェント: \[[\w-]+\] 形式で単一指定のみ（複数指定は検証項目8でエラー）
使用Skill の値部分が以下の正規表現にマッチするか:
  単一: \[[\w-]+\] または \[steering:[\w.-]+\]
  複数: 上記パターンのカンマ区切り（, で区切り）
対応UIデザイン: ui-design-url\.md(「[\w-]+」)+（https://www\.figma\.com/design/...）形式
インデント:
  タスクグループ配下 → 行頭2スペース
  タスク配下 → 行頭4スペース
```

### 8. サブエージェント複数指定検証

- [ ] `実行サブエージェント` にカンマ区切りの複数指定がないか（グループレベル・タスクレベル両方）
- [ ] 1タスクグループ/1タスクにつき1サブエージェントのみであること

**検出ロジック**:
```
実行サブエージェント の値にカンマ（,）が含まれている場合はエラー
例: [frontend-coder], [backend-architect] → multiple_subagents エラー
```

### 9. UIタスクの「対応UIデザイン」必須チェック

UIタスクと判定されるタスク（X.Y.Z）に `対応UIデザイン` フィールドが存在しない場合はエラー。

**UIタスク判定条件（以下のどちらかに該当）**:
1. タスク名または説明に以下のキーワードを含む: `UI`、`画面`、`フォーム`、`コンポーネント`、`レイアウト`
2. サブタスク内容（実装内容）に `*.tsx`、`*.css`、`*.scss` のファイルパターンを含む

**バックエンド専用タスクの除外（UIタスクから除外）**:
以下の条件のみに該当する場合は UIタスクから除外し、`対応UIデザイン` は不要:
- 実装対象が `*.ts` のみ（`*.tsx` を含まない）
- 実装対象が `packages/server-core/**` のみ
- migration / schema のみの変更

**エラーメッセージ**:
```
UIタスク '{タスク名}' には「対応UIデザイン」フィールドが必要です。ui-design-url.md の対応フレーム名を指定してください。例: 「ui-design-url.md「users-list」（https://www.figma.com/design/XXXX?node-id=123-456）」
```

**検出ロジック**:
```
各タスク（X.Y.Z）を走査し、以下を判定する:

Step1: UIタスク判定
  - タスク名または直下のサブタスク行に UIキーワード（UI/画面/フォーム/コンポーネント/レイアウト）が含まれる
  - または サブタスク内容に tsx/css/scss のファイルパターンが含まれる
  → どちらかに該当 → UIタスク候補

Step2: バックエンド専用タスク除外
  UIタスク候補のうち、以下の全条件を満たす場合は除外:
  - .tsx / .css / .scss のパターンを含まない
  - かつ packages/server-core のみ、または migration/schema のみを示す記述がある
  → 除外対象 → チェック不要

Step3: 対応UIデザイン存在チェック
  UIタスク候補（除外対象を除く）に `対応UIデザイン:` メタデータが存在しない場合 → missing_ui_design エラー
```

## エラー種別

| 種別 | 説明 |
|------|------|
| `missing_metadata` | 必須メタデータが欠落 |
| `invalid_indent` | インデントが不正 |
| `invalid_id_format` | ID形式が不正 |
| `invalid_dependency` | 依存関係の書式が不正 |
| `missing_dependency_target` | 依存先が存在しない |
| `too_many_phases` | Phase数が多すぎる |
| `horizontal_split` | 横切り分割（アンチパターン） |
| `horizontal_split_keyword` | タスクグループ名に禁止ワードが含まれる |
| `fundamental_format_violation` | Task X-Y等のフォーマット根本違反（即FAILURE） |
| `missing_bold_metadata` | メタデータキーが太字でない |
| `missing_hierarchy` | Phase/タスクグループ/タスクの3階層構造がない |
| `invalid_optional_metadata_format` | 任意メタデータ（実行サブエージェント / 使用Skill / 対応UIデザイン）の形式が不正 |
| `multiple_subagents` | 実行サブエージェントに複数指定がある（グループ・タスク両方で禁止） |
| `missing_ui_design` | UIタスクに「対応UIデザイン」フィールドが存在しない |
