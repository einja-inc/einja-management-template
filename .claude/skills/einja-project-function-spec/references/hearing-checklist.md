# ヒアリングチェックリスト（einja-project-function-spec）

本ファイルは `einja-project-function-spec` Skill が AskUserQuestion で使う質問テンプレ集である。
**1業務フロー = 1ファイル（function-spec-{flow_id}.md）の §1〜§7 に 1:1 対応** する 7 質問構成。

本ファイルは以下の 4 点を扱う:
1. AskUserQuestion 用の質問テンプレ集（Q1〜Q7、業務フロー単位）
2. function-spec-{flow_id}.md 各セクションへの Edit マッピング（質問ID → セクションマッピング）
3. 再開推定ロジック（Step 0.2 で参照される）
4. Step 0 詳細フォールバック（モード推定の細則）

## 使用上の原則

- **1業務フロー = 1ヒアリングセッション**（Q1〜Q7 を順次。並列ヒアリングは行わない）
- **選択肢は 2-4 個**（4 個超は別 Q に分割）
- **「その他（自由入力）」を必ず含める**（CLAUDE.md 準拠）
- **「決まっていない / 未定」も明示的に選択肢に含める**（推測禁止）
- **業務観点優先**: 技術的詳細（API・DB スキーマ・実装方式）は §7 未確定事項に申し送り、本Skillでは扱わない
- **screen-flow-url.md 連携**: `stable_id` を画面参照キーとして用い、関連画面選択時は screen-flow-url.md の `screens[]` から選択肢を動的構成する
- **`description` (What) と `Note:` (So What) の 2 層記述** で選択肢を提示する

## 質問テンプレ Q1〜Q7

### Q1: 業務フロー概要 — AS-IS / TO-BE 要約

**質問**: この業務フロー（`{flow display name}`）の AS-IS（現状）と TO-BE（あるべき姿）の要約を確認します。`requirements.md §2.1.1 / §2.1.2` から推定される要約を提示しますので、修正や補足を指示してください。

| ラベル | description (What) | Note (So What) |
|--------|-------------------|----------------|
| そのまま採用 | requirements.md §2 から抽出した要約をそのまま §1 に転記 | メリット: 最速、要件定義との整合性が自動的に保たれる。デメリット: 業務フロー単位の粒度では情報が薄いことがある |
| 補足追記 | 要約に業務フロー固有の補足（背景・トリガー・頻度等）を追記する | Note: 追記内容を自由入力で指定。requirements.md §2.2 業務課題と解決方針の該当行も併記推奨 |
| AS-IS のみ大幅修正 | TO-BE は採用、AS-IS は現場ヒアリングで判明した詳細に置き換える | Note: AS-IS の正確性が運用設計に影響する場合に使用 |
| TO-BE のみ大幅修正 | AS-IS は採用、TO-BE は本Skillで改めて設計する | Note: 要件定義と TO-BE 認識がずれている場合に使用 |
| その他（自由入力） | 上記以外の指示 | - |

### Q2: アクター一覧 — 関与する利用者・システム・外部システム

**質問**: この業務フローに登場するアクターを確定します。`requirements.md §3 対象ユーザー` と `§2.1.2 mermaid subgraph 名` から推定された候補を提示しますので、選択・追加してください。

`multiSelect: true`

| ラベル | description (What) | Note (So What) |
|--------|-------------------|----------------|
| {推定アクター: 利用者ロール（複数）} | requirements.md §3 から抽出した利用者ロール（例: 一般従業員、上長、人事担当） | Note: §3.3 権限マトリクスのロールと整合性を取る |
| {推定アクター: システム} | 「新システム」「アプリ」等の自社システム | Note: sequenceDiagram の `participant System as 勤怠SaaS` 等で表現 |
| {推定アクター: 外部システム} | §9 外部連携要件で言及される外部システム（例: 給与計算SaaS、IdP） | Note: §9 連携先一覧と integration_id 等を引用 |
| 全アクター採用 | 上記推定値をすべて採用 | Note: 最速。Q3 メッセージ授受で詳細化する |
| その他（自由入力） | 推定外のアクターを追加 | Note: アクター名を自由入力（例: 「監査部 / 経理担当」） |

### Q3: 業務フロー詳細 — メッセージ授受・分岐・例外

**質問**: この業務フローの時系列インタラクション（誰が誰に何を依頼・通知するか）を確定します。mermaid `sequenceDiagram` で記述するため、主要なメッセージ授受・分岐（alt）・任意処理（opt）を整理します。

| ラベル | description (What) | Note (So What) |
|--------|-------------------|----------------|
| 基本フローのみ（分岐なし） | 「正常系」一本道で記述。例外は §5 業務ルールで別途扱う | メリット: 図がシンプル。デメリット: 承認・差し戻し等の分岐が多い業務には不向き |
| 基本フロー + 主要分岐 | `alt 承認/差し戻し` 等の 1-2 個の主要分岐を含む | Note: 推奨。多くの業務で必要十分 |
| 基本フロー + 分岐 + 例外処理 | `alt` + `opt` で例外（エラー時の代替フロー等）も明示 | Note: 監査要件が厳しい業務・SLAが厳しい業務向け |
| 詳細手順を自由入力で記述 | アクター・メッセージ・分岐を自由入力で指定 | Note: 自由入力欄で `participant ...` `A->>B: ...` 等の sequenceDiagram フラグメントを直接記述可 |
| その他（自由入力） | 上記以外の指示 | - |

選択後、必要に応じて Skill 側で「ステップ別表」（ステップ番号 / アクター / 操作 / 関連画面 stable_id / 関連機能ID / 入出力 / 例外）を sequenceDiagram と1:1対応で生成する。

### Q4: 機能一覧 — このフローで使う機能（FN-XXX 採番）

**質問**: この業務フローで使う機能を確定します。`FN-XXX` は本Skill独立採番（`requirements.md §6` の機能IDとは別系統）です。

| ラベル | description (What) | Note (So What) |
|--------|-------------------|----------------|
| §2 sequenceDiagram のメッセージから自動抽出 | Q3 で確定したメッセージ授受 1 件 = 1 機能として `FN-XXX` 自動採番 | Note: 推奨。最速で網羅性高い。優先度は全 `MUST` 初期値、後で個別調整可 |
| §6 機能要件サマリから関連機能を選択 | requirements.md §6.1 機能一覧から関連する機能を選択して本Skill側で `FN-XXX` 再採番 | Note: requirements.md 側 ID と本Skill側 `FN-XXX` の対応表は §3 機能一覧表の備考列に記載 |
| 機能を自由入力で列挙 | 機能名 / 概要を自由入力で列挙、本Skill側で `FN-XXX` 採番 | Note: §2 / §6 のどちらにもない補助機能（バリデーション・通知等）も追加可 |
| その他（自由入力） | 上記以外の指示 | - |

各機能には以下を確定する（Edit テンプレ側で表形式管理）:
- `FN-XXX`（採番） / 機能名 / 概要 / 関連画面 stable_id / 関連業務ステップ番号 / 優先度（MUST/SHOULD/MAY）

### Q5: データの流れ — システム間連携・データ授受

**質問**: この業務フローでシステム間連携・データ授受が発生しますか？

| ラベル | description (What) | Note (So What) |
|--------|-------------------|----------------|
| 外部システム連携あり（API・ファイル） | §9 外部連携要件で言及される外部システムとデータ授受 | Note: 連携方式（REST API / SFTP / Webhook 等）・データ形式（JSON/CSV/PDF）・タイミング（同期/非同期/バッチ）を確定 |
| 内部システム間連携あり（マイクロサービス・バッチ） | 同一プロジェクト内でモジュール間連携が発生 | Note: モジュール境界・連携I/Fを §4 に記載。設計フェーズで詳細化する申し送り事項を §7 に追記 |
| 単一システム内完結 | この業務フローは1つのシステム/モジュール内で完結 | Note: §4 を `<!-- SKIPPED: 該当なし -->` に置換 |
| 未確定 | データの流れが現時点で不明 | Note: §7 未確定事項に登録、設計フェーズで詳細化 |
| その他（自由入力） | 上記以外 | - |

### Q6: 業務ルール・バリデーション（業務観点）

**質問**: この業務フローで適用する業務ルール・承認フロー・例外処理を確定します。

`multiSelect: true`

| ラベル | description (What) | Note (So What) |
|--------|-------------------|----------------|
| 承認フローあり | 申請 → 承認 → 完了の業務フロー（多段承認含む） | Note: 承認者ロール・差し戻し条件・期限切れ時の動作を §5 に明記 |

## 質問ID → セクションマッピング

各質問IDが function-spec-{flow_id}.md のどのセクションに反映されるかの対応表。SKILL.md Step 2 のEditループで参照する。

### マッピング表

| 質問ID | 主セクション | 直前見出し（Editアンカー用） | 波及セクション | スキップ可否 |
|--------|-------------|------------------------|-------------|-----------|
| Q1 | §1 業務フロー概要 | `## 1. 業務フロー概要` | - | 不可 |
| Q2 | §1 アクター一覧 + §2 アクター宣言 | `### 1.2 アクター` | §2 sequenceDiagram の `participant` 行 | 不可 |
| Q3 | §2 業務フロー詳細（sequenceDiagram + ステップ別表） | `## 2. 業務フロー詳細` | - | 不可 |
| Q4 | §3 機能一覧 | `## 3. 機能一覧` | - | 不可 |
| Q5 | §4 データの流れ | `## 4. データの流れ` | §7（連携詳細を設計フェーズへ申し送り） | 可 |
| Q6 | §5 業務ルール・バリデーション | `## 5. 業務ルール・バリデーション（業務観点）` | - | 可 |
| Q7 | §6 関連画面一覧 + §7 未確定事項・前提条件 | `## 6. 関連画面一覧` | §7 | 不可（§6は不可、§7は実質可） |

#### スキップ可否の運用ルール

- すべての質問に対し AskUserQuestion 実行時には「スキップ（後回し）」「該当なし（恒久スキップ）」を必ず選択肢に含める
- マッピング表で「スキップ可否=不可」の質問は、ユーザーが「該当なし（恒久スキップ）」を選択した場合、警告を出し「本当に該当なしで確定しますか？」と再確認する。確定された場合は Step 3 残存チェックで欠落として扱う
- 「スキップ（後回し）」は全質問で許可する（後で Step 3 残存検出から拾えるため）

### Edit時のアンカー戦略

- `old_string` は **「直前見出し行 + 直後のプレースホルダ含む行（またはテンプレ表の代表行）」のペア**で構成し、`replace_all: false` で実行する
- 主セクションを最初に置換した後、波及セクション（特に Q2 の §2 sequenceDiagram `participant` 行追記）があれば該当セクションのテンプレ部分も追加 Edit する
- プレースホルダ形式は `\[ [^\]]+? \]`（`[ スペース XXX スペース ]`）の1形式のみ
- **代表プレースホルダ行の選び方**: テンプレ上の見出し直下の最初の `[ ... ]` プレースホルダ行を採用する

## 再開推定ロジック（Step 0.2 詳細）

`docs/project/function-specs/index.md` が既存の場合、以下の順で再開地点を推定する:

### 推定ステップ

1. `index.md` frontmatter から `function_specs[]` の配列を取得
2. 各 entry の `file` パスから `function-spec-{flow_id}.md` を Read
3. 各ファイルの残存プレースホルダ（`\[ [^\]]+? \]` 形式）を全件スキャン
4. プレースホルダが残っている flow_id の集合を「未完了フロー」として保持
5. 未完了フローの中で、Q1（§1）から順にスキャンし「最も若い未回答質問」を推定開始質問とする
6. 推定結果を Step 0.3 のモード選択質問文に「進行状況: 未完了 N フロー、推定再開地点 {flow_id} の {Q-ID}」形式で含める

### 推定結果の信頼性表示

- 推定結果には**判定根拠**（埋め済み判定の最終 Q-ID、判定対象 flow_id 一覧）を必ず添える
- 例: 「flow_id=`attendance-saas__flow__time_punch` は Q4 まで完了と推定。次は Q5 から開始。」
- 推定が外れている場合に備え、モード選択肢の「E: その他（自由入力）」で再開位置を手動指定できるようにする

## Step 0 詳細フォールバック

SKILL.md Step 0 で扱いきれない細則を以下に集約する。

### `index.md` frontmatter スキーマ未知の `schema_version`

- `index.md` の `schema_version` が本Skillの対応バージョンと一致しない場合は Skill 読み込みを停止し、ユーザーに Skill 更新を促す
- 対応バージョンは `references/manifest-schema.md` §5 拡張性ポリシー を参照

### `project_name` 確定方法

優先順位:
1. `screen-flow-url.md` frontmatter の `project_name`（存在すれば最優先・正本扱い）
2. `requirements.md` frontmatter または §0 文書情報の「プロジェクト名」を kebab-case 化
3. 両方で確定不能なら AskUserQuestion で kebab-case 文字列を直接ユーザーに入力させる

### `flow_id` 命名規則の詳細

- 形式: `{project_name}__flow__{snake_case_flow_name}`
- `project_name` 部分は kebab-case（例: `attendance-saas`）
- `flow_name` 部分は snake_case（例: `time_punch_approval`）
- 区切りは `__`（アンダースコア2つ）で screen-flow-url.md の `stable_id` 規則（`{project_name}__{name}`）と整合
- 例: `attendance-saas__flow__time_punch_approval`

### `requirements.md §2` からの業務フロー候補抽出ヒント

- 主要シグナル: `### 2.1.2 TO-BE 業務フロー` の見出し直下 mermaid `flowchart` の subgraph 名（アクター名）+ §2.2 業務課題と解決方針の表の課題ID
- 補助シグナル: §2.3 業務ルール、§6.1 機能一覧の機能名グルーピング
- 抽出失敗時のフォールバック: §6.1 機能一覧の全機能を 1:1 で `{機能名}-フロー` として業務フロー化（最低限のセーフティネット）

### `screen-flow-url.md` の `stable_id` 動的選択肢生成

Q7（関連画面選択）の AskUserQuestion 選択肢は、`screen-flow-url.md` の `screens[]` を Read して動的構成する:

- screens[] から `name` と `stable_id` を抽出
- 4件以下なら全件を選択肢に並べる
- 5件以上なら頻出推定上位3件を選択肢に並べ、残りは「その他（自由入力）」で stable_id をカンマ区切り指定

## スキップマーカー仕様

- ユーザーが「該当なし（恒久スキップ）」を選んだ場合、対応セクションの主要プレースホルダを `<!-- SKIPPED: 該当なし -->` に置換する
  - テーブル内の行は1行目を置換し残り行は削除可
  - mermaid `sequenceDiagram` 全体を該当なしにする場合は ``` ブロック全体を `<!-- SKIPPED: 該当なし -->` で置換
- ユーザーが「スキップ（後回し）」を選んだ場合、プレースホルダはそのまま残す
- Step 3 残存チェックでは `SKIPPED` マーカーを「OK扱い（恒久スキップ）」、`[ ... ]` プレースホルダ残存を「警告対象」とする
- **空配列リテラルの扱い**: `related_screens: []` / `related_function_ids: []` は frontmatter の正常な空配列状態として残存プレースホルダカウントに **含めない**。プレースホルダ正規表現 `\[ [^\]]+? \]` は中身を持つ `[ 説明文 ]` 形式のみマッチするため自動的に除外されるが、AskUserQuestion時には「該当画面なし」「該当機能なし」を選択させる際の明示として活用する。
- index.md の `status` 判定:
  - 残存プレースホルダが0件（`SKIPPED` マーカーは0件カウント）→ `review`
  - 残存プレースホルダが1件以上 → `draft`
  - ユーザーが Step 4 でレビュー完了を承認 → `approved`（手動で frontmatter 編集してもよい）
