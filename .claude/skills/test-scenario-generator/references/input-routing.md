## 1. 入力ソース 2 種一覧

| ソース | 形式 | 強み | 弱み | 主経路 or 補助経路 |
|--------|------|------|------|-----|
| 自然言語の自由入力 | テキスト | 起動コストが最も低い・反復生成に向く | テスト範囲・対象モジュールの曖昧さが残る | 主経路 |
| git diff | `HEAD` / `HEAD~1` / 任意レンジ | 既存実装に対する後付けテストに最適 | 意図を推測する必要がある | 補助経路（既存実装テスト時の主軸） |

## 2. 判定木

起動時の引数・ユーザーメッセージ・カレントディレクトリ状態を解析して経路を決定する。

```
START
  │
  ├─ git diff を取りたい指示（「diff から」「最近の変更」「今の変更分」等）か? ─ Yes ─▶ [A] git diff
  │
  ├─ 上記に該当しない自然言語か? ─ Yes ─▶ [B] 自然言語
  │
  └─ 入力種別が判別できない ─▶ [Q] AskUserQuestion で確認
```

### 判定の補足

1. **明示指示の優先**: 「diff から」「git diff」「最近の変更に対して」等、変更差分を明示的に指す発話があれば [A] を優先する
2. **判別不能時**: 入力種別を 1 つに絞れない場合は [Q] へ進む。推測で進めず必ず確認する

## 3. ルート別詳細手順

### [A] git diff 入力時

```yaml
steps:
  1: 対象パッケージで `git diff --name-only --diff-filter=AM {range}` を実行
     - range 未指定時は `HEAD` を既定値とする（AskUserQuestion で確認してもよい）
  2: 変更ファイルを test ファイル（*.test.ts, *.spec.ts 等）と非 test ファイルに仕分け
  3: 非 test ファイルごとに `git diff {range} -- {file}` で差分内容を取得
  4: 差分内容からシナリオ候補（関数・コンポーネント単位の変更点）を抽出し、
     SKILL.md Step 3（種別判定）へ渡す
```

**Bash 例（対象範囲の差分取得）**:

```bash
git diff --name-only --diff-filter=AM HEAD~1 -- {対象パッケージ相対パス}
```

### [B] 自然言語入力時

```yaml
steps:
  1: ユーザーの自由入力をそのままシナリオ材料として保持する
  2: 対象モジュール・機能名が明言されていない場合は AskUserQuestion で確認する
     （選択肢例: 「対象ファイルを指定する」「対象ディレクトリで検索する」「その他（自由入力）」）
  3: 複数のシナリオが 1 発話に含まれる場合は文単位・要求単位で分割する
  4: 分割したシナリオ群を SKILL.md Step 3（種別判定）へ渡す
```

## 4. 複数併用時の優先順位

- git diff の指示と自然言語での補足説明が同時に来た場合、git diff をベースシナリオとし、自然言語部分は補足情報（対象の絞り込み・除外指示等）として扱う
- 明確な優先順位が付けられない場合は AskUserQuestion で確認する

## 5. fail-closed の挙動詳細

以下のケースはテスト生成を中止し、ユーザーへ理由と代替案を提示する（推測で進めない）:

| ケース | 提示する代替案 |
|--------|--------------|
| git diff 対象範囲に変更ファイルが 0 件 | 「対象範囲を変更する」「自然言語で入力し直す」「その他（自由入力）」 |
| 自然言語入力が抽象的すぎてシナリオ化不能 | 「対象ファイル・機能名を教えてください」と再質問 |
| git diff 実行が失敗（対象パッケージが git 管理外等） | 「自然言語で入力し直す」「中止する」「その他（自由入力）」 |

---

## 6. AskUserQuestion の使い分け

- 入力種別の判別: 選択肢は「git diff から生成」「自然言語で説明する」「その他（自由入力）」
- git diff の対象範囲確認: 「直近のコミット（HEAD~1）」「ステージ済み変更のみ」「その他（自由入力・レンジ指定）」
- いずれも選択肢の最後は必ず「その他（自由入力）」とする
