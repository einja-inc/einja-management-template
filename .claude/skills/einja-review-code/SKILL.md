# einja-review-code Skill: 必須10視点による観点別並列コードレビュー

あなたはシニアコードレビュアーです。コード変更の品質を**必須10視点（A-J）**で多角的に検証し、構造化された判定結果を返却します。この10視点は「出荷可否を左右する必須の親軸」であり、**適用条件で条件ピックせず、毎回すべて評価する必須フロア**です（該当する変更がない視点も、silent skip せず「該当なしPASS＋根拠」を明示する）。**視点B〜JはStep 3で並列レビュアーとして評価し、視点A（リリース品質＝統合視点）はStep 4.5でB〜Jの結果を統合して最終評価します**（Aは他視点の結果に依存するため並列では起動しない）。

## 必須レビュー10視点（親軸）

10視点はすべて**必須（常に評価）**。B〜Jは並列レビュアーで、A（統合視点）はStep 4.5で評価する。各視点の「下位項目」は具体的なチェック内容であり、diffに該当がある項目を重点的に見る。下位項目に「※条件」が付くものは、その条件に合致する変更がある場合に適用する（例: Skill設計チェックはSKILL.md変更時のみ）。

## 実行フロー

### Step 1: 変更内容の把握

```bash
git diff HEAD --stat
git diff HEAD
```

`git diff HEAD` を使用し、ステージ済み・未ステージの両方の変更を含める。変更がない場合は「変更なし」として即座にPASS判定を返却する。

### Step 1.5: Codex MCP利用可否の事前確認

ToolSearchで `mcp__codex__codex` が利用可能か確認する。この結果に基づいてStep 3でCodexレビュアーを呼び出すか判断する。

### Step 2: 視点の割り当てとレビュアー構成（必須フロア＋コスト緩和）

**視点B〜J（9視点）はすべて必須。条件ピックで視点を落とすことはしない**（視点Aは統合視点のためStep 4.5で評価）。Step 1で取得したdiffのファイルパスと変更内容から、各視点について「重点的に見る下位項目」と「深さ」を決める。

> **用語**: 本Skillを実行する主体（CLAUDE.mdの99-1実行者、task-reviewer等の呼び出し元エージェント）を「**統括**」と呼ぶ。統括はレビュアーの起動・結果統合・Step 4.5のリリース品質評価を担う。各視点のAgent tool（general-purpose）を「レビュアー」、`codex-agent` を「Codexレビュアー」と呼ぶ。

**割り当てルール:**
- **視点B〜Jすべてをレビュー対象にする**（毎回評価）。各視点の下位項目のうち、diffに該当する箇所を重点的にレビューする。
- **該当する変更が全く無い視点も silent skip しない**。その視点のレビュアーは「該当変更なし。確認した範囲と根拠」を述べたうえで **PASS** を返す（偽PASS排除＝『黙って飛ばす』の禁止）。
- ※条件付き下位項目（例: 視点DのSkill設計チェックはSKILL.md変更時のみ、視点Fのadmin/token系・dataflow lensは該当変更がある時）は、条件に合致する場合のみ深掘りする。

**コスト緩和（機械的バッチ委任ルール）:**
「毎回B〜Jを独立レビュアーで起動」を原則としつつ、**統括直読でのPASSショートカットは禁止**（透明性・偽PASS排除のため、全視点は必ず独立Agentがレビューする）。コスト過大を避けるため、以下の**機械的条件**を満たす軽量変更時のみ、該当の薄い複数視点を**1体のレビュアーにバッチ委任**してよい（＝独立Agent起動は維持しつつ、Agent数を減らす）:
- **発動条件（すべて満たす）**: ①`git diff HEAD --stat` の変更行数合計が **50行未満** ②変更ファイルが **コード実行系・環境/デプロイ系を含まない**。コード実行系＝`apps/**`・`packages/**/src/**`・API/route/DB/migration/scripts/CI設定。環境/デプロイ系（視点J該当）＝`Dockerfile`・`railwayignore`・`package.json`・lockfile（`pnpm-lock.yaml`等）・`.env`系・CI/デプロイ設定。これらを1つでも含む場合はバッチ委任不可（＝純粋なドキュメント・SKILL.md・設定コメントのみのとき発動）
- **視点J該当ファイルの例外**: 環境/デプロイ系ファイルが変更に含まれる場合、視点Jは軽量変更でも**常に専任レビュアーで起動**する（バッチ委任の「薄い視点」に落とさない）
- **バッチ委任の作法**: 深掘り対象でない複数視点を1体のレビュアーに渡し、**視点ごとに個別の判定（PASS/MINOR/MAJOR）と根拠**を返させる。深掘り対象の視点は専任レビュアーで起動する。
- 上記条件に該当しない（コード実行系を含む・50行以上）変更では、**B〜Jを個別の専任レビュアーで起動する**（バッチ委任しない）。

**割り当て例（重点の付け方。挙げていない視点も必ずレビュー対象＝該当なしPASSまたは指摘を記録）:**
- `apps/web/src/hooks/useAuth.ts` + `LoginForm.tsx`（コード実行系・専任起動）→ F（認証＝セキュリティ）, C（回帰・後方互換）, D（コード品質）, H（エラーハンドリング）を深掘り。B/E/G/I/J も専任レビュアーが該当範囲を確認しPASS/指摘。A は Step 4.5 で統合評価。
- `.claude/skills/einja-foo/SKILL.md` のみ（50行未満・非コード実行系 → バッチ委任可）→ D（Skill設計チェックリスト）, I（ドキュメント）を深掘り。該当の薄い B/C/E/F/G/H/J は1〜2体にバッチ委任し各視点の判定を記録。A は Step 4.5。
- APIルート/DB操作/バックグラウンドジョブ（コード実行系・専任起動）→ C（回帰・マイグレーション）, F（セキュリティ）, G（パフォーマンス・多重送信）, H（可観測性・縮退）を深掘り。B/D/E/I/J も専任で確認。A は Step 4.5。
- LLM/外部API呼び出しを含む変更（コード実行系・専任起動）→ G（呼び出し回数・多重送信・冪等性）, H（タイムアウト・リトライ・縮退）, F（スキーマ整合・secrets）を深掘り。その他視点も専任で確認。A は Step 4.5。

```
ここでは判定せず、リリースブロッカー候補があれば参考情報として報告してください）:
B:完了条件・本質課題(PO) / C:回帰 / D:コード品質 / E:テスト網羅性・自動検知 /
F:セキュリティ / G:パフォーマンス・コスト / H:エラーハンドリング・可観測性 /
I:ドキュメント・仕様整合 / J:環境差分・デプロイ整合
のいずれの隙間も埋めるつもりで、特に以下を重点的に確認してください:
- B（完了条件・本質課題）: 受入条件が形式的に満たされても本質課題が未解決でないか。PO目線の価値が出ているか
- G（パフォーマンス・コスト）: LLM/API呼び出し回数・多重送信・冪等性欠如による多重実行
- H（エラーハンドリング・可観測性）: 本番縮退・503/408・タイムアウト/リトライ・ログの適切性
- J（環境差分・デプロイ整合）: env・feature flag・本番/stg差分・Dockerfile/NODE_ENV

判定（PASS/MINOR/MAJOR）と指摘事項を報告してください。

対象ファイル一覧:
{git diff HEAD --stat出力}

変更差分:
{git diff HEAD出力}
```

### エラーハンドリング

- **必須視点（B〜J）のレビュアーがエラーで失敗した場合**: **再起動を必須とする**（最低1回）。再起動しても完了できない場合、その視点は **PASSにできない**。最終判定を **MAJOR（レビュー未完了）** とし、Step 5表の該当視点は判定「**未完了(SKIP)**」・レビュー方式「**失敗（再起動不能）**」と明記する（silent skip＝暗黙のPASS扱いを禁止）
- **diffが巨大すぎる場合（目安: 2000行超）**: `git diff HEAD --stat` ベースでファイル一覧のみ提示し、レビュアーに個別ファイルの読み込みを指示する
- **Codexレビュアーがタイムアウト/エラーの場合**: Codex結果なしで統合判定を継続（「Codex MCP利用不可のためスキップ」と同じ扱い）

### Step 4: レビュー結果の統合（B〜J＋Codex）

視点B〜Jの全レビュー結果とCodexレビュー結果を統合する。

#### 統合ルール
- 視点B〜JとCodexレビューの判定のうち**最も厳しい判定**を採用する（MAX判定）
- MAJOR > MINOR > PASS の順
- Codexレビューの指摘は、可能な限り該当視点（A〜J）にマッピングして記録する
- この段階の統合結果（特にCodexが視点Aにマッピングした参考情報・リリースブロッカー候補）を、Step 4.5の視点A評価の入力として引き継ぐ

### Step 4.5: リリース品質（視点A）の最終評価

視点B〜Jの結果が出揃った後、**統括が視点A（リリース品質＝統合視点）を評価する**。B〜Jで並列に評価できない「出荷可否の総合判断」をここで担う:
- B〜Jの全指摘を**出荷可否の重み**で評価し、**リリースブロッカー**（MAJOR相当で本番投入を止めるべき問題）を明示する
- 技術的な堅牢性（異常入力・境界での破綻）・保守性（可読性・凝集度・将来の変更容易性）を、変更全体を俯瞰して総合判断する
- 視点Aの判定（PASS/MINOR/MAJOR）を出す

※ユーザー価値・本質課題の充足は視点B（Step 3で評価済み）の担当であり、Aでは重複評価しない。

#### 最終判定（A〜J＋Codex のMAX判定）
- 視点A〜J **およびCodexレビュー** のうち**最も厳しい判定**を最終判定とする
- いずれかがMAJOR → 最終MAJOR / MAJORなしでいずれかがMINOR → 最終MINOR / 全員PASS → 最終PASS
- レビュアー失敗で完了できない必須視点がある場合は、PASSにできず最終判定はMAJOR（レビュー未完了）とする（上記エラーハンドリング参照）

## 判定基準

| 判定 | 基準 | 後続アクション |
|------|------|---------------|
| **PASS** | 指摘なし | 完了判定の必須チェックに進む |
| **MINOR** | 軽微な指摘（命名、コメント、軽微なリファクタ等） | 修正後、再レビュー不要 |
| **MAJOR** | 設計レベルの問題（アーキテクチャ違反、セキュリティ、重大なバグ、受入条件/本質課題の未達、リリースブロッカー） | ユーザーに報告し、修正方針を確認 |

## 呼び出し元からのコンテキスト受け渡し

このSkillは以下のコンテキストを受け取ることができる:
- **react-doctor結果**: 呼び出し元（task-reviewer等）がreact-doctor診断を実行済みの場合、その結果テキストをSkill呼び出し時の引数や前置テキストとして渡す。各視点サブエージェントのプロンプトに「参考情報」として埋め込む（主に視点D/E/Gで活用）
- **レビュー対象の限定**: 特定のファイルやディレクトリに限定したレビューが必要な場合、呼び出し元がdiffの範囲を指定できる
- **受入条件/spec**: 視点B（完了条件・本質課題）の精度向上のため、呼び出し元は requirements.md / Issue AC / spec のパスまたは内容を渡せる。渡された場合、視点Bレビュアーのプロンプトに埋め込み、受入条件を1件ずつトレースさせる
