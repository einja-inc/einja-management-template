# einja-review-code Skill: 観点別並列コードレビュー

あなたはシニアコードレビュアーです。コード変更の品質を**観点別の並列レビュー**で多角的に検証し、構造化された判定結果を返却します。

## レビュー観点一覧

| ID | 観点名 | 説明 | 適用条件 |
|----|--------|------|----------|
| A | Skill設計 | `einja-skill-plan-guide` ワークフローBのチェックリストに照らしたSkill固有品質レビュー | SKILL.mdの変更を含む場合 |
| B | コード・ロジック | 設計パターン整合性、型安全性、プロジェクト規約準拠、コード品質 | コード変更がある場合（ほぼ常時） |
| C | セキュリティ・エラーハンドリング・異常系 | OWASP Top 10、入力バリデーション、エラー伝播、異常系パス | API・認証・外部入力・DB操作等の変更がある場合 |
| D | 整合性 | 既存コードベースとの一貫性、後方互換性、型・インターフェース整合 | 複数ファイル変更、公開API変更がある場合 |
| E | 影響範囲・水平展開 | 他モジュールへの波及、同種パターンの水平適用漏れ、未使用コード残存 | リファクタリング、共通ロジック変更の場合 |
| F | テスト観点 | テストカバレッジ、テストケース不足、境界値・異常系テスト | テストの追加・変更、またはテスト追加が必要な本体変更の場合 |
| G | ドキュメント作成・更新漏れ | README、JSDoc、CLAUDE.md、Skill説明文、steering docs等の更新必要性 | 公開API変更、設定変更、新機能追加の場合 |

## 実行フロー

### Step 1: 変更内容の把握

```bash
git diff HEAD --stat
git diff HEAD
```

`git diff HEAD` を使用し、ステージ済み・未ステージの両方の変更を含める。変更がない場合は「変更なし」として即座にPASS判定を返却する。

### Step 1.5: Codex MCP利用可否の事前確認

ToolSearchで `mcp__codex__codex` が利用可能か確認する。この結果に基づいてStep 3でCodexレビュアーを呼び出すか判断する。

### Step 2: 観点ピック（適用する観点の選定）

Step 1で取得したdiffの**ファイルパス**と**変更内容**から、レビュー観点一覧の「適用条件」に基づいて必要な観点をピックする。

**ピックルール:**
- 各観点の「適用条件」にdiffの内容が合致するかを判定
- **観点B（コード・ロジック）は常にピック**（コード変更がある限り）
- 判断が曖昧な場合は**ピックする**（見落としより過剰レビューを優先）
- ドキュメントのみの変更の場合は観点Gのみ
- ピック結果を記録し、Step 3のプロンプトに含める

**ピック例:**
- `apps/web/src/hooks/useAuth.ts` + `apps/web/src/components/LoginForm.tsx` が変更 → B（コード）, C（セキュリティ: 認証関連）, D（整合性: 複数ファイル）
- `.claude/skills/einja-foo/SKILL.md` のみ変更 → A（Skill設計）, G（ドキュメント）
- `packages/shared/src/utils.ts` の共通関数リファクタ → B（コード）, D（整合性）, E（影響範囲）

### Step 3: 観点別並列レビューの実行

ピックした観点ごとにレビュアー（Agent tool, general-purpose）を**1つのメッセージで複数同時に**起動する。Codex MCP有効時は Codexレビュアー（Agent tool, `codex-agent`）も同時に起動する。

> **用語**: 本Skillでは各観点のAgent toolを「レビュアー」、CLAUDE.md委託ルールで定義されたカスタムサブエージェント `codex-agent` を「Codexレビュアー」と呼ぶ。

#### 各観点レビュアーのプロンプトテンプレート

```
あなたはシニアコードレビュアーです。以下のgit diffを【{観点名}】の観点でレビューしてください。

## レビュー観点: {観点ID}. {観点名}
{観点の説明}

## 参照すべきドキュメント
- `docs/einja/steering/development/coding-standards.md` - コーディング規約
- `docs/einja/steering/development/review-guidelines.md` - レビューガイドライン
{観点Aの場合: - `.claude/skills/einja-skill-plan-guide/SKILL.md` の「ワークフローB: Skill実装レビュー」セクションのチェックリストを使用}

{react-doctor結果がある場合}
## react-doctor診断結果（参考情報）
{react-doctor結果}
{/react-doctor結果がある場合}

## 出力形式

### 判定: [PASS / MINOR / MAJOR]

#### 指摘事項（ある場合）
- **ファイル:行番号**: 指摘内容
  - 修正案: 具体的な修正方法

#### 良い点（任意）
- 良かった点があれば記載

## 対象diff:
{git diff HEAD出力}
```

#### Codexレビュアー【Step 1.5でCodex MCP有効と判定された場合のみ】

Agent toolで `codex-agent` を起動し、**包括的・批判的な目線**での独立レビューを依頼する:

```
以下のコード変更を包括的・批判的な目線でレビューしてください。
各観点レビュアーが見落とす可能性のある横断的な問題（設計の一貫性、命名の統一性、
変更全体の整合性など）に注目してください。

判定（PASS/MINOR/MAJOR）と指摘事項を報告してください。

対象ファイル一覧:
{git diff HEAD --stat出力}

変更差分:
{git diff HEAD出力}
```

### エラーハンドリング

- **レビュアーがエラーで失敗した場合**: 該当観点をスキップし、他のレビュアーの結果で統合判定を継続。スキップした観点を結果に明記する
- **diffが巨大すぎる場合（目安: 2000行超）**: `git diff HEAD --stat` ベースでファイル一覧のみ提示し、レビュアーに個別ファイルの読み込みを指示する
- **Codexレビュアーがタイムアウト/エラーの場合**: Codex結果なしで統合判定を継続（「Codex MCP利用不可のためスキップ」と同じ扱い）

### Step 4: レビュー結果の統合

全レビュー結果を統合し、最終判定を決定する。

#### 統合ルール
- 全レビュアーの判定のうち**最も厳しい判定**を最終判定とする（MAX判定）
- MAJOR > MINOR > PASS の順
- いずれかのレビュアーがMAJOR → 最終MAJOR
- MAJORなしでいずれかがMINOR → 最終MINOR
- 全員PASS → 最終PASS

### Step 5: 結果返却

以下の形式で返却する:

```markdown
## 完了レビュー結果

### 最終判定: [PASS / MINOR / MAJOR]

### ピックされた観点
{ピックされた観点ID・名前のリスト}

### 各観点レビュー結果
#### 観点{ID}（{観点名}）: [判定]
{レビュー結果の全文}

（ピックされた各観点について繰り返し）

### Codexレビュー: [判定 / スキップ]
{レビュー結果の全文 or "Codex MCP利用不可のためスキップ"}

### 統合サマリー
- 指摘数: N件（MAJOR: X, MINOR: Y）
- 対応方針: {PASS→完了判定へ / MINOR→修正後再レビュー不要 / MAJOR→ユーザーに報告}
```

## 判定基準

| 判定 | 基準 | 後続アクション |
|------|------|---------------|
| **PASS** | 指摘なし | 完了判定の必須チェックに進む |
| **MINOR** | 軽微な指摘（命名、コメント、軽微なリファクタ等） | 修正後、再レビュー不要 |
| **MAJOR** | 設計レベルの問題（アーキテクチャ違反、セキュリティ、重大なバグ） | ユーザーに報告し、修正方針を確認 |

## 呼び出し元からのコンテキスト受け渡し

このSkillは以下のコンテキストを受け取ることができる:
- **react-doctor結果**: 呼び出し元（task-reviewer等）がreact-doctor診断を実行済みの場合、その結果テキストをSkill呼び出し時の引数や前置テキストとして渡す。各観点サブエージェントのプロンプトに「参考情報」として埋め込む
- **レビュー対象の限定**: 特定のファイルやディレクトリに限定したレビューが必要な場合、呼び出し元がdiffの範囲を指定できる
