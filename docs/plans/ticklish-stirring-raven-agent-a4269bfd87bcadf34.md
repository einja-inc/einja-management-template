# einja-issue-team-exec ピア間通信活用再設計 計画

## Context

現行の `einja-issue-team-exec` は Lead が全ゲートチェックを一手に担い、Director（Teammate）間の直接通信はゼロ。Agent Teamsの最大の差別化特徴である SendMessage によるピア間通信を全く活用できていない。

合意済み設計方針:
- Lead の役割（Phase管理・ゲートチェック・CI監視・人間窓口）は維持+拡張
- Director の役割を拡張: ピアレビュー（他Directorの変更レビュー）+ 変更通知（完了時ブロードキャスト）

---

## 現状

### 現行フロー（通信パターン）

```
Director A ──SendMessage──▶ Lead（ゲートチェック）
Director B ──SendMessage──▶ Lead（ゲートチェック）
Director C ──SendMessage──▶ Lead（ゲートチェック）
```

- Director 同士の通信: ゼロ
- Lead が全ての情報ハブ: ゲートチェック・CI監視・マージ・Phase完了判定をすべて実施
- Director は「タスクを実行してPRを上げてLeadに報告する」だけの役割

### 問題点

1. Lead がボトルネック: 全PRの Fast Gate / Risk Gate を Lead 1体が担当
2. 設計的な非一貫性の検出が遅い: 複数Directorが同じ共有リソースを違う形で実装してしまっても、Leadのゲートチェック時まで気づけない
3. Agent Teamsの活用度が低い: ピア間通信能力が使われていない

---

## 各観点の分析と提案

### 観点1: ピアレビューのタイミング問題

**問題**: DirectorがTask X.1実装中にDirector X.2からレビュー依頼が来た場合どうするか？

**リスク分析**:
- 自タスクを中断してレビュー対応 → 実装の文脈断絶、品質低下リスク
- 完了後にレビューするとしても、X.2がレビュー応答を待っている間ブロックされる → デッドロックに近い状況

**推奨アプローチ: 非同期非同期ピアレビュー**

Director が自タスクのPR作成・コミット完了後、ブロードキャストを送信する。受信側 Director は自分のタスク実装「完了後」に非同期でレビューを実施する。つまり:

- ブロードキャスト送信タイミング: 自タスクのPR作成・コミット完了後（awaiting_review 遷移前）
- ブロードキャスト受信・レビュー実施タイミング: 受信側の次のアイドルタイム（クリーンアップ後 or 次タスクclaimの前）
- ピアレビュー結果の用途: Lead への補足情報として提出（Leadのゲートチェックを補完するが、ゲートをブロックしない）

これにより「中断」問題を完全回避し、デッドロックも防止できる。

**代替案（採用しない）: 割り込みレビュー**
- 受信時に即時レビュー対応
- 問題: 自タスクを中断するコストが大きく、実装品質が下がる可能性。並列処理の利点が薄れる

---

### 観点2: デッドロック防止

**リスク**: 全DirectorがPR作成完了 → 全員が互いのピアレビューを待つ → 全員がブロックされる

**現象の特定**:
```
Director A: PR作成完了 → "B, Cをレビューするまで次に進めない"
Director B: PR作成完了 → "A, Cをレビューするまで次に進めない"
Director C: PR作成完了 → "A, Bをレビューするまで次に進めない"
→ 全員待ち状態
```

**根本原因**: ピアレビューが「次タスクclaimの前提条件」になっている設計

**解決策: ピアレビューを非同期・非ブロッキング化**

ピアレビューは:
- **完了後にできれば実施する** というベストエフォート型とする
- 次タスクのclaimをブロックしない
- レビュー結果はLeadへのメッセージとして送信（Leadが情報を蓄積）
- Lead は十分な情報が集まった時点でゲートチェック判断に活用

具体的な遷移:
```
Director A: タスク完了 → ブロードキャスト送信 → 次タスクclaimを試みる
  ↓ 次タスクがない場合（アイドル）
Director A: 未レビューの通知を確認 → 可能な範囲でレビュー → Lead に送信
```

これによりデッドロック完全防止。

---

### 観点3: ステータス遷移へのピアレビュー組み込み方法

**現行のステータス遷移**:
```
pending → in_progress → awaiting_review → completed
```

**awaiting_review の意味変化**:
- 現行: 「LeadによるFast Gate/Risk Gate待ち」
- 拡張後: 「LeadによるFast Gate待ち AND ピアレビュー情報収集中（非ブロッキング）」

**推奨アプローチ: ステータス定義に変更なし、補助情報として管理**

ステータス遷移自体は変えない。代わりに TaskList のメタデータ（description）にピアレビューの受領状況を記録する形にする:

```
TaskUpdate: description に追記
  peerReviews:
    - from: director-N
      receivedAt: ISO8601
      summary: "...重複なし、設計整合性OK..."
```

これにより:
- プロトコル全体の変更を最小化できる
- issue-exec-protocol.md の改訂が不要（または軽微）
- ピアレビューが得られた場合にLeadのRisk Gate判断の参考情報になる

---

### 観点4: ピアレビューの品質保証

**形骸化リスク**: ピアレビューが「承認しました」だけになる

**原因分析**: ピアレビュー実施のインセンティブがなく、実施コストに見合うフィードバックが期待されない

**推奨アプローチ: チェックリスト駆動 + フォーマット強制**

ピアレビューに以下の構造化チェックリストを必須とする:

```markdown
## Peer Review Report: Task {X.Y} by Director-{N}
Reviewer: Director-{M}

### 確認観点
- [ ] 共有リソース重複: 自タスクと同じファイルを変更していないか
- [ ] API/型定義の整合性: 自タスクで定義した型・APIと矛盾しないか
- [ ] コンフリクト予防: git mergeで衝突しそうな変更がないか
- [ ] 設計整合性: issue全体の設計方針と乖離していないか

### 判定
- CLEAN: 問題なし
- WARNING: 軽微な注意点あり（Lead判断参考情報）
- CONCERN: 要確認（LeadにエスカレーションをCONCERN理由とともに送信）

### 所見
{具体的な観察内容 or "問題なし"}
```

CONCERN判定の場合のみLeadが即時アクションを取る（awaiting_review中のDirectorに確認）。CLEAN/WARNINGはLeadへの情報提供で終了。

---

### 観点5: 変更通知のフォーマット

**何を伝えるべきか**:

ピアレビューに有用な情報を絞る。変更されたファイルの全リストは不要（長すぎる）。判断に必要な構造的情報を伝える。

**推奨フォーマット**:

```markdown
[peer-broadcast] Task {X.Y} 完了通知
PR: #{PR番号}
Branch: task/{N}-{X.Y}

## 変更サマリー
- 変更ファイル数: N個
- 主要変更: {ファイルパスと変更の概要 3件まで}

## 共有リソース
- 追加/変更したAPI: {エンドポイント一覧 or "なし"}
- 追加/変更したDB schema: {テーブル/カラム or "なし"}
- 追加/変更した型定義: {型名・ファイルパス or "なし"}
- 新規追加した共有コンポーネント: {コンポーネント名 or "なし"}

## 注意点
{他Directorへの申し送り事項 or "なし"}
```

**ポイント**:
- 「共有リソース」セクションが最重要: ここにコンフリクト・重複の種がある
- 全変更ファイルの列挙は不要（PRを見ればわかるため）
- 3件までの主要変更で十分な情報量を確保

---

### 観点6: Leadゲートチェックとの二重チェック問題

**懸念**: ピアレビュー + Leadゲートで同じことを2回チェックして冗長にならないか？

**結論: 役割分担を明確化することで冗長性を解消できる**

| チェック観点 | ピアレビュー（Director）| Leadゲートチェック（Fast Gate） |
|------------|----------------------|-------------------------------|
| 成果物存在確認 | しない | する（QA記録・PR整合性） |
| CI結果確認 | しない | する |
| 共有リソース重複 | **する** | しない（知識がない） |
| コンフリクト予防 | **する** | しない（Leadは全変更を把握困難） |
| 設計整合性 | **する** | 表面的にのみ（コード読まない） |
| 危険シグナル検知 | しない | する（TODO/FIXME等） |

ピアレビューはLeadが苦手な「横断的整合性チェック」に特化し、LeadはLeadが得意な「成果物の完全性チェック・プロセス管理」に集中する。二重チェックではなく**補完関係**。

**ただし注意点**:
- CONCERN判定のピアレビューが来た場合、Leadは Fast Gate に加えて追加調査を実施する
- ピアレビューがない（全Directorが実装中）ケースでも、LeadのFast Gateは通常通り実施（ピアレビューはあくまでボーナス情報）

- `.claude/skills/einja-issue-team-exec/SKILL.md` — Director Teammates プロンプトテンプレートと Step 5 監視ループを拡張

### Director Teammateプロンプトの変更点

**追加: 変更通知（ブロードキャスト）**

PR作成・コミット完了後、awaiting_review 遷移前に SendMessage でチーム全員（Leadを含む）へブロードキャスト:

```
Step 4（新規）: 変更通知ブロードキャスト
- 全 Teammate に [peer-broadcast] フォーマットで変更通知を送信
- Leadにも同内容を送信（Lead は受信ログとして記録）
- その後 awaiting_review 遷移・Lead に完了報告
```

**追加: ピアレビュー実施（アイドル時）**

自タスク完了後、次タスクがない場合（アイドルタイム）またはクリーンアップ後に実施:

```
Step 7.5（新規）: アイドル時ピアレビュー
- 未レビューのブロードキャストを確認
- チェックリスト形式でピアレビューを実施
- 結果を Lead に SendMessage（CONCERN の場合は即時エスカレーション）
- 次タスクのclaimに優先度は与えない（ピアレビューはベストエフォート）
```

### Leadの監視ループ変更点

**Step 5-1 メッセージ種別に追加**:

| メッセージ種別 | 対応 |
|--------------|------|
| `[peer-broadcast]` 変更通知 | ログとして記録。他DirectorへのメッセージはDirectorが処理（Lead介入不要） |
| `[peer-review]` ピアレビュー結果 | CLEAN/WARNING → Fast Gate補足情報として蓄積。CONCERN → 対象Directorに追加確認を指示 |

### issue-exec-protocol.md の変更点

セクション 1.3（方式別責務差分）に追記:

```
| ピアレビュー（横断的整合性） | tmux版: なし | Agent Teams版: Director（ベストエフォート）|
```

## リスク・不明点

### リスク1: ピアレビューのオーバーヘッド

全Directorが互いをレビューすると、Nタスク × (N-1)回のレビューが発生する。5体のDirectorプールであれば最大20回。

**緩和策**:
- ピアレビューはアイドル時のみ実施（自タスク完了後・次タスクclaimまでの隙間）
- チェックリスト形式で所要時間を短縮
- 全員がレビューしなくても、できた分だけLeadに送るベストエフォート方式

### リスク2: ブロードキャストメッセージの取りこぼし

SendMessageが非同期のため、Director が自タスク実装中に届いたブロードキャストを見逃す可能性。

**緩和策**:
- DirectorはTaskList経由で受信メッセージキューを確認（または SendMessage の仕様に依存）
- 取りこぼしても致命的でない（LeadのFast Gateは独立して動作）

### リスク3: CONCERN判定の濫用

Directorが些細な点で CONCERN を出しすぎると、Leadが対応に追われる。

**緩和策**:
- CONCERN の定義を「マージするとCIが落ちる可能性が高い」レベルに限定する
- Directorプロンプトで CONCERN 基準を厳格に定義する

### 不明点

- Agent Teams の SendMessage は「特定Teammate指定」か「ブロードキャスト」かの仕様詳細（実装時に要確認）
- Teammate が他のTeammate の ID を知る方法（TeamCreate 時に全Teammate IDが既知か確認要）

## 検証・動作確認方法

1. **SKILL.md の構造確認**: Director プロンプトテンプレートに変更通知・ピアレビュー手順が追加されていること
2. **issue-exec-protocol.md の確認**: セクション 1.3 にピアレビューの記載があること
3. **目視レビュー**: ブロードキャストフォーマット・チェックリストフォーマットが完全かつ一貫しているか
4. **整合性確認**: ピアレビューが Lead の Fast Gate をブロックしない設計になっているか（非ブロッキング確認）

## 設計判断サマリー（独立した視点からの率直な意見）

### 採用する設計
1. **非同期・非ブロッキングのピアレビュー**: デッドロック防止の観点から必須。ピアレビューを次タスクclaimの前提条件にしない
2. **アイドル時実施**: 「自タスク完了後・次タスクclaimまでの隙間」という自然なタイミングを活用
3. **補完的役割分担**: ピアレビューは「横断的整合性」、Leadゲートは「成果物完全性」に特化。二重チェックを排除
4. **チェックリスト強制**: 形骸化防止のため、観点と判定基準を構造化

### 懸念点（率直に）
- **効果が限定的な可能性**: 実際のプロジェクトでは、タスクグループ間のファイル重複が少ない設計になっている場合、ピアレビューのCONCERN率はほぼゼロになる。設計投資に対するリターンが薄い可能性がある
- **実装コストが想定より高い可能性**: SendMessage の具体的な API 仕様（Teammate ID の取得方法、メッセージキューの参照方法）によっては、Director プロンプトの複雑度が大幅に増す
- **最重要の未解決課題**: Agent Teams の SendMessage で「Teammate が他の Teammate に直接メッセージを送れるか」という根本的な仕様が未確認。LeadにしかSendMessageできない仕様であれば、本設計全体が成立しない。**実装前に Agent Teams の仕様検証が必須**
