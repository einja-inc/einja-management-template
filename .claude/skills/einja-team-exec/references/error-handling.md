# エラーハンドリング・Circuit Breaker 詳細

このドキュメントは `SKILL.md` の Step 1-F で参照されるエラーハンドリング詳細仕様。

---

## Teammate 停止検知

| 状態 | 検知 | 対応 |
|------|------|------|
| Director 停止（タスク実行中） | idle 通知 + タスクが in_progress のまま | 新 Teammate spawn（最大2回）→ 3回目はユーザー報告 |
| Director 停止（完了報告済み） | idle 通知 + 成果物あり | スキップ（verdict 処理を継続） |

---

## タスク連続失敗（Circuit Breaker）

同一タスクが **3回連続失敗** した場合、タスクを中断（status を `failed` に設定）し、
AskUserQuestion でユーザーにエスカレーションする。

### AskUserQuestion の選択肢（2層記述）

各選択肢は CLAUDE.md「AskUserQuestion 選択肢の記述ルール」に従い、
`description`（What）と `Note:`（So What）の2層で記述する。

| ラベル | description（What） | Note（So What） |
|-------|---------------------|---------------|
| 手動で修正して再開 | ユーザーが該当箇所を手動で修正し、Lead がタスクを再キュー | メリット: 失敗原因を直接解消できる。デメリット: ユーザーの作業時間が必要。リスク: 修正中、他タスクは待機状態となる |
| タスクをスキップ | 該当タスクと依存タスクをまとめてスキップ | メリット: セッション全体を継続可能。デメリット: 依存タスクの成果物が欠落。リスク: 後工程で再対応が必要 |
| セッションを終了 | 全 Teammate をクリーンアップしてセッションを終了 | メリット: 安全に停止できる。デメリット: 完了済みタスクの成果物は手動マージが必要。リスク: 再開時に状態復元できない |
| その他（自由入力） | 追加指示を自由入力 | メリット: 想定外シナリオに対応可能。デメリット: 入力内容によっては解釈が必要。リスク: 曖昧な指示はさらなる確認が必要 |

---

## 全体セッションタイムアウト

- デフォルト: **2時間**
- タイムアウト到達時: graceful shutdown（Step 1-G）を実行
- ユーザーに完了状況と未完了タスクを報告

---

## その他のエラー

| 障害 | 対応 |
|------|------|
| git lock エラー | jitter 付き 1-2秒待機 → 再試行（最大3回）→ abort |
| マージコンフリクト | `einja-conflict-resolver` Skill 呼び出し |
| GitHub API 認証失敗 | ユーザーに通知して停止 |
| Worker silent failure（30分タイムアウト） | タスクを failed 扱い → 再キュー（最大2回）→ ユーザー報告 |
| SendMessage 取りこぼし | シグナルファイルで検知 → TaskList 再確認 → 不整合なら Director に ping |
