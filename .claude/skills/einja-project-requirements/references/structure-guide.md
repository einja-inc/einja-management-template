## 1. 全体方針

- **クライアント合意用文書**: 平易な日本語で書く。専門用語は §1.4 用語定義で補足するか括弧書きで言い換える。可能な限り表・mermaid 図を使う
- **推測禁止**: ビジネス要件（業務目的・KPI・ステークホルダー・運用ルール等）はユーザー以外決められない。判明していない情報は AskUserQuestion で確認するか `（未確定: 〇〇のため次回ヒアリング）` と明示する。技術的事実（一般的なアーキテクチャパターン等）は自力調査可
- **柔軟性**: 該当しない章は省略せず「該当なし」と明示（空欄禁止）。例: 新規開発で移行不要 → §10 に「該当なし（新規開発のため）」
- **見積もり・コストは含めない**: 工数・金額・単価は別文書（見積書・契約書）に分離。本書では参照のみ
- **画面一覧は §6 に含めない**: 画面構成は Figma / `ui-design-url.md` 側で管理。要件定義書では機能・バッチ・帳票のみ扱う
- **対比語の統一**: 「クライアント」「発注側」は同義（クライアント = 発注側 = 顧客企業）、「受託側」「自社」も同義（受託側 = 自社 = 開発側）。本書冒頭の §1.4 用語定義に対応関係を必ず明記し、本文では「発注側 / 受託側」を主表記とする

## 2. 章別記入ガイド

### §0 文書情報 / Sources

#### 目的
版管理と参照源の明示。誰がいつ何を根拠に作ったかを追跡可能にする。

#### 記入のポイント
- 版番号（例: `v0.1 / v1.0`）と発行日を必ず記載
- Sources 表に IPA/JIS/JUAS の主要参照リソース＋クライアント提供資料を列挙

#### 品質チェックリスト
- [ ] 版番号・日付が記載されている
- [ ] Sources 表に最低3件以上の参照源がある
- [ ] クライアント提供資料がある場合は出典が明記されている

### §1 プロジェクト概要

#### 目的
プロジェクトの背景・目的・KPI・用語をクライアントと共有する。

#### 記入のポイント
- **背景**: ビジネス文脈で書く（「業務効率化」のような抽象語ではなく具体的な課題）
- **目的**: 1〜2文で簡潔に
- **KPI**: 測定可能な指標を1〜3個（例: `受注処理時間 30分→5分`）
- **用語定義**: クライアント側で揺れる用語のみ。一般的IT用語は不要

#### 主参照源
IPA「超上流から攻めるIT化の事例集」、共通フレーム（SLCP）

#### 品質チェックリスト
- [ ] 背景がビジネス文脈で記述されている
- [ ] KPI が測定可能な数値指標である
- [ ] 用語定義に揺れやすい業務用語が登録されている

#### よくあるミス
- KPI に「向上する」「改善する」など測定不能な語を使う → 必ず数値・時間・件数で表現

### §2 対象業務（AS-IS / TO-BE）

#### 目的
現状業務（AS-IS）と将来業務（TO-BE）の差分を可視化し、システム化による変化点を合意する。

#### 記入のポイント
- **AS-IS / TO-BE 両方必須**（Plan承認済み）
- mermaid `flowchart TD` + `subgraph` でスイムレーン記法を使う
- 業務課題と解決方針を AS-IS / TO-BE の差分で説明
- 各業務フローは「アクター」「主要アクション」「分岐条件」を含む

#### 主参照源
IPA「超上流から攻めるIT化の事例集」、共通フレーム

#### 品質チェックリスト
- [ ] AS-IS フローが mermaid で描かれている
- [ ] TO-BE フローが mermaid で描かれている
- [ ] 差分（システム化された箇所）が明示されている
- [ ] mermaid のシンタックスエラーがない

#### よくあるミス
- TO-BE だけ書いて AS-IS を省略 → 課題の説得力が出ない。両方必須
- フロー図にアクター（誰が）が欠落 → subgraph でスイムレーン化する

### §3 対象ユーザー・ステークホルダー

#### 目的
関係者を網羅し、決裁者と利用者を区別する。

#### 記入のポイント
- ペルソナは「具体的な役職・業務内容・1日の使い方」まで踏み込む
- 決裁者（経営層・部門長）と利用者（オペレーター・現場）を明確に分けて表記
- 体制図は mermaid `graph TB` で簡潔に

#### 主参照源
IPA「超上流から攻めるIT化の事例集」、共通フレーム

#### 品質チェックリスト
- [ ] 決裁者・利用者の区別がついている
- [ ] 各ペルソナに役職と業務内容が記載されている

### §4 システム化方針

#### 目的
パッケージ/スクラッチ/SaaS/ハイブリッドの選定理由とアーキテクチャ方針の高レベル合意。

#### 記入のポイント
- 採用方針の選定根拠を明記（コスト・拡張性・既存資産活用等）
- アーキテクチャ方針は mermaid `graph TB` で高レベル（DB・主要サービスのみ）に留める。詳細設計は `design.md` 側

#### 主参照源
JIS X 0166（要件定義プロセス）

#### 品質チェックリスト
- [ ] 採用方針（パッケージ/スクラッチ/SaaS等）と選定根拠が記載されている
- [ ] アーキテクチャ図が概念レベルに留まっている（実装詳細を含まない）

### §5 スコープ境界

#### 目的
「含む / 含まない」を明示し、後工程でのスコープクリープを防ぐ。

#### 記入のポイント
- 含む / 含まない を表形式で明示
- フェーズ分割がある場合は MVP / Phase2 / Phase3 を分けて記載

#### 主参照源
JIS X 0166

#### 品質チェックリスト
- [ ] 含む / 含まない が表で記述されている
- [ ] フェーズ分割がある場合は MVP 範囲が明確

### §6 機能要件サマリ

#### 目的
機能・バッチ・帳票の一覧をID/名称/概要の3列で提示する。

#### 記入のポイント
- **画面一覧は含めない**（Plan制約）。画面構成は Figma / `ui-design-url.md` で管理
- 機能一覧 / バッチ一覧 / 帳票一覧の3つの表
- 各行は `ID（F-001等）/ 名称 / 概要（1文）`

#### 主参照源
IPA「機能要件の合意形成ガイド」

#### 品質チェックリスト
- [ ] 機能一覧表がある
- [ ] バッチ一覧表がある（該当なしの場合は明示）
- [ ] 帳票一覧表がある（該当なしの場合は明示）
- [ ] 画面一覧が含まれていない
- [ ] 各機能にIDが付与されている

### §7 非機能要件

#### 目的
JUAS非機能要求グレードの6大項目を表形式で要約する。

#### 記入のポイント
- **表形式で要約**（フル展開しない、Plan承認済み）
- 6大項目: 可用性 / 性能・拡張性 / 運用・保守性 / 移行性 / セキュリティ / システム環境・エコロジー
- 各項目に**具体的な数値目標**を入れる（例: `稼働率 99.5% / 月次計画停止 2時間以内`）

#### 主参照源
IPA/JUAS「非機能要求グレード」

#### 品質チェックリスト
- [ ] 6大項目すべてが表に記述されている
- [ ] 各項目に数値目標がある
- [ ] 表形式で要約されている（章ごとに節を切らない）

#### よくあるミス
- 「高可用性を担保する」など定性的記述で終わる → 必ず数値（%・時間・件数）に落とす

### §8 データ要件

#### 目的
主要エンティティの業務概念モデルとデータ量を共有する。

#### 記入のポイント
- ERDは**業務概念レベル**（論理ER）。物理データモデル（テーブル定義・カラム型）は `design.md` 側
- データ量は現状＋将来見積もり（3年後等）も含める

#### 主参照源
JIS X 0166、共通フレーム

#### 品質チェックリスト
- [ ] ERD が業務概念レベルに留まっている
- [ ] データ量に将来見積もりが含まれている

### §9 外部連携要件

#### 目的
連携先・連携方式・データ仕様を3点セットで合意する。

#### 記入のポイント
- 連携先（システム名・ベンダー）/ 連携方式（API/CSV/FTP等）/ データ仕様（フォーマット・頻度）を必ず3点セットで
- 連携がない場合は「該当なし」と明示

#### 主参照源
JIS X 0166、共通フレーム

#### 品質チェックリスト
- [ ] 各連携に「連携先・方式・データ仕様」3点が揃っている

### §10 移行要件

#### 目的
データ移行・業務移行のリスクと方針を共有する。

#### 記入のポイント
- 移行リスクは特に重要（移行失敗はプロジェクト全体に波及）
- 新規開発で移行不要の場合は「該当なし（新規開発のため）」と明記

#### 主参照源
IPA/JUAS「非機能要求グレード」

#### 品質チェックリスト
- [ ] 移行対象データの範囲が明示されている
- [ ] 該当なしの場合は理由付きで明示されている

### §11 運用・保守要件

#### 目的
運用時間帯・障害対応SLA・保守範囲を合意する。

#### 記入のポイント
- 運用時間帯（24/365 / 営業日9-18時 等）
- 障害対応SLA（重大度別の応答・復旧時間）
- 保守範囲（バグ修正のみ / 軽微改修込み 等）

#### 主参照源
IPA/JUAS「非機能要求グレード」

#### 品質チェックリスト
- [ ] 運用時間帯が明示されている
- [ ] 障害対応SLAが重大度別に記述されている

### §12 プロジェクト体制と役割

#### 目的
受託側と発注側の役割分担を明示する。

#### 記入のポイント
- **受託側と発注側の役割分担表が必須**
- RACI（責任・実行・相談・通知）で記述すると明瞭

#### 主参照源
共通フレーム

#### 品質チェックリスト
- [ ] 受託側と発注側の役割分担表がある

### §13 スケジュール

#### 目的
マイルストーンと主要フェーズを共有する。

#### 記入のポイント
- マイルストーン日付を明示
- **見積もり・コストは含めない**（Plan制約）。別文書参照とする
- mermaid `gantt` 記法が使えると望ましい

#### 主参照源
共通フレーム

#### 品質チェックリスト
- [ ] マイルストーン日付が記載されている
- [ ] 見積もり・コスト情報が含まれていない

### §14 品質保証

#### 目的
品質目標と受入基準の概要を共有する。

#### 記入のポイント
- 品質目標と受入基準のみ（概要）
- テスト戦略・テストケース詳細は `qa-test.md` 参照

#### 品質チェックリスト
- [ ] 品質目標が記載されている
- [ ] 受入基準が記載されている
- [ ] 詳細は qa-test.md 参照と明記されている

### §15 リスクと前提

#### 目的
想定リスクと前提条件を共有し、変更時の合意基準を作る。

#### 記入のポイント
- 想定リスクは**発生確率と影響度を表**で（高/中/低）
- 前提条件（クライアント側で守られる事項）も明示

#### 主参照源
IPA「超上流から攻めるIT化の事例集」

#### 品質チェックリスト
- [ ] リスク表に発生確率と影響度がある
- [ ] 前提条件が列挙されている

### §16 合意事項・変更管理

#### 目的
本書の承認とその後の変更管理ルールを明示する。

#### 記入のポイント
- **承認欄テーブル + 版歴表が必須**
- 変更管理プロセス（影響度別の承認フロー: 軽微/中規模/大規模、承認者と承認期限）を明記
- リポジトリ上では PR / Issue で運用するが、本書では業務プロセス（変更管理委員会・ステアリング承認等）を記述する

#### 主参照源
共通フレーム

#### 品質チェックリスト
- [ ] 承認欄テーブルがある（受託側・発注側）
- [ ] 版歴表がある
- [ ] 変更管理プロセス（影響度別承認フロー）が明記されている
- [ ] 変更管理ルール（PR/Issue ベース）が明記されている
