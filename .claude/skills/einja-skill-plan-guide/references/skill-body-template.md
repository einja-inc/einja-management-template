# SKILL.md本文 責務・入出力 定義テンプレート

新規スキル作成時、SKILL.md本文に以下6セクションを含める。目的はスキル間の責任範囲と入出力を統一フォーマットで宣言し、連携ミス（呼ぶ側が入力を間違える・責務の重複や漏れが起きる）を防ぐこと。

## 1. 6項目の雛形

新規スキルのSKILL.md本文（概要の直後）に、以下6セクションをこの順序で含める。下記コードブロックをそのままコピーし、各プレースホルダを埋めること。

```markdown
## 責務
{達成する唯一の主目的を動詞1〜2文。「〜し、かつ〜する」と複数並ぶ場合は分割を検討}

## スコープ外（やらないこと）
- {やらないこと}（→ {委譲先スキル名} の責務）

## 使用タイミング
- 呼び出し元: {ユーザー直接 / スキル名 / サブエージェント名}
- 局面: {どのフェーズ・どのタイミングで呼ばれるか}

## 入力
### 必須入力
- `{名前}`: {型/形式} — {説明}
### オプション入力
- `{名前}`: {型/形式} — {説明}（{いつ渡されるか}）

## 出力
- 形式: {ファイル / パス / 文字列 / 構造化データ 等}
- 内容: {出力の骨子}

## 依存スキル
| 依存スキル | 条件 |
|-----------|------|
| `{スキル名}` | {どの条件で呼ぶか} |
（内部で他スキルを呼ばない場合は「なし」）
```

## 2. 各項目の記法ルール

| 項目 | 何を書くか | 粒度の目安 |
|------|-----------|-----------|
| **責務** | このスキルが達成する唯一の主目的。動詞で言い切る | 1〜2文。1スキル1責務。「〜し、かつ〜する」と接続詞で並ぶなら分割サイン |
| **スコープ外** | 責務の裏側。混同されやすいが「やらないこと」を、委譲先スキル名つきで明示 | 該当する隣接スキルの数だけ箇条書き。委譲先が無いものは書かなくてよい |
| **使用タイミング** | 誰が（呼び出し元）・いつ（局面）呼ぶか | 呼び出し元と局面の2行。複数あれば列挙 |
| **入力** | 呼ぶ側が渡す値。名前＋型/形式＋説明を必ず3点セットで書く | 必須とオプションを分ける。オプションは「いつ渡されるか」も添える |
| **出力** | このスキルが返すもの。形式を明示（ファイル / パス / 文字列 / 構造化データ 等） | 形式1行＋内容の骨子1行。呼ぶ側が受け取り方を判断できること |
| **依存スキル** | 内部で呼ぶ他スキルと、その呼び出し条件 | 表形式で列挙。呼ばないなら「なし」と明記 |

### 補足

- **責務**: 「〜を生成する」「〜を検証する」のように動作を主語にする。名詞の羅列（「タスク管理」）は避ける
- **スコープ外**: 「入力/出力が近い」「名前が似ている」隣接スキルとの境界を切るためのセクション。委譲先を書くことで、呼ぶ側が正しいスキルへ誘導される
- **入力/出力**: 呼ぶ側が迷わないことが目的。入力は名前・型・説明、出力は形式・内容を欠かさない。「よしなに受け取る」のような曖昧記述は禁止
- **依存スキル**: 空欄にせず、無ければ「なし」と書く。空欄は「書き忘れ」と区別がつかないため

## 3. 分類別の記入指針

einjaのスキルは3分類あり、分類によって各項目の読み替え方が変わる。該当しない項目は空欄にせず `N/A（{理由}）` と明記する。

| 分類 | 例 | 入力の読み替え | 出力の読み替え | 依存スキル |
|------|-----|--------------|--------------|-----------|
| **タスク型**（明確なI/Oを持つ） | `_einja-issue-spec-tasks-generator` | 全項目を素直に埋める | 全項目を素直に埋める | 呼ぶなら列挙、呼ばないなら「なし」 |
| **参照型**（情報提供のみ） | `_einja-output-format`, `_einja-project-overview` | 「参照する側が渡す文脈（あれば）／なし」と読み替える | 「提供する情報の骨子」と読み替える | 通常「なし」。該当しない項目は `N/A（参照型のため）` |
| **オーケストレーター**（ユーザーと対話しワークフローを進める） | `einja-issue-spec-create` | ユーザー指示 / 引数 | 最終成果物 | 必ず埋まる（内部で複数スキルを呼ぶため） |

- **タスク型**: 入力→処理→出力が明確なので、雛形をそのまま埋めれば成立する
- **参照型**: 独立したタスク指示を持たず情報を提供するだけ。`入力`は原則「なし」（参照側が文脈を渡す設計なら明記）、`出力`は「提供する情報の骨子」。`使用タイミング`以外で該当しない項目は `N/A（参照型のため）` と書く
- **オーケストレーター**: ユーザー入力を起点に複数スキル・サブエージェントを束ねる。`依存スキル`は必ず埋まるので、主要な委譲先を漏れなく列挙する

## 4. 完成記入例

### 例1: タスク型

`_einja-issue-spec-tasks-generator`（Issue仕様タスク生成スキル）に6項目フォーマットを当てはめた記入例。元のSKILL.mdは4見出し構成のため、「スコープ外」「依存スキル」を内容から補完している。

```markdown
## 責務
requirements.md と design.md に基づき、GitHub Issue本文用のタスク一覧（Phase → タスクグループ → タスク → サブタスク）を生成する。

## スコープ外（やらないこと）
- 生成したタスクのフォーマット検証・差し戻し判定は行わない（→ _einja-issue-spec-tasks-validator の責務）
- 要件定義・設計そのものの作成は行わない（→ requirements-generator / design-generator の責務）

## 使用タイミング
- 呼び出し元: tasks-generator サブエージェント
- 局面: einja-issue-spec-create のタスク生成フェーズ（要件・設計確定後）

## 入力
### 必須入力
- `spec_directory`: パス — requirements.md / design.md / qa-tests/ を含む仕様書ディレクトリ
- `issue_number`: 数値 — 更新対象のGitHub Issue番号
### オプション入力
- `error_feedback`: Markdown文字列 — バリデーション失敗時のエラーレポート（差し戻し時に渡され、これを元に修正版を生成）

## 出力
- 形式: Markdown文字列（GitHub Issue本文）
- 内容: AS-IS / TO-BE / 対応方針 と、メタデータ付きタスク一覧（Phase・タスクグループ・タスク・サブタスク階層）

## 依存スキル
| 依存スキル | 条件 |
|-----------|------|
| なし | 内部で他スキルは呼ばず、steering の task-management.md を参照するのみ |
```

### 例2: 参照型

`_einja-output-format`（サブエージェント統一出力形式スキル）に6項目フォーマットを当てはめた記入例。参照型のため、`入力`は「なし」、`出力`は「提供する情報の骨子」、該当しない項目は `N/A` と明記している。

```markdown
## 責務
全サブエージェントが従うべき統一出力形式（標準構造・エージェント別テンプレート・長い出力の扱い）を定義し、参照側に提供する。

## スコープ外（やらないこと）
- 出力内容そのものの生成・実行は行わない（各サブエージェントの責務）
- 出力が形式に準拠しているかの検証は行わない（呼び出し元エージェントの責務）

## 使用タイミング
- 呼び出し元: 各サブエージェント（frontend-coder / backend-architect / codex-agent 等）
- 局面: サブエージェントが最終出力を組み立てる直前

## 入力
- なし（参照側が渡す文脈は不要。定義済みの出力形式を読み取るのみ）

## 出力
- 形式: N/A（参照型のため。処理結果を返さず、参照される定義そのものが提供物）
- 内容: 標準出力構造、エージェント別テンプレート、長い出力の details 折りたたみ規則、失敗・エラー時の記述ルール

## 依存スキル
| 依存スキル | 条件 |
|-----------|------|
| なし | 情報提供のみで他スキルを呼ばない |
```

### 例3: オーケストレーター型

`einja-issue-spec-create`（Issue仕様書作成スキル）に6項目フォーマットを当てはめた記入例。ユーザー指示を起点に複数のサブエージェント・スキルを束ねてワークフローを進めるため、オーケストレーター型では `依存スキル` が必ず埋まる（内部で呼ぶ委譲先を漏れなく列挙する）。

```markdown
## 責務
ユーザー指示（Issue番号・要件・Asana/Figma URL等）を起点に、ATDDベースのIssue仕様書一式（requirements.md / ui-design-url.md / design.md / qa-test.md）を段階的に生成し、GitHub Issueへのタスク一覧記述とSpec PR作成までを統括する。

## スコープ外（やらないこと）
- 要件定義書・設計書・QA仕様・タスク一覧の本体生成は自身では行わない（→ requirements-generator / design-generator / qa-generator / tasks-generator サブエージェントの責務）
- 仕様書レビューの実施判定は自身では行わない（→ einja-review-spec の責務）
- 仕様書に基づく実装・コード変更は行わない（→ einja-issue-exec / einja-task-exec の責務）

## 使用タイミング
- 呼び出し元: ユーザー直接（Issue仕様書を新規作成 or 既存Issueへ追加・変更するとき）
- 局面: 実装着手前の仕様策定フェーズ（Phase 0 前提確認 → Phase 1 要件 → Phase 2 設計・UI・QA → Phase 3 タスク記述）

## 入力
### 必須入力
- `user_instruction`: 自然言語 — 対象Issueの機能名・要件・スコープ等の指示
### オプション入力
- `issue_number`: 数値 — 既存Issueを操作する場合の対象Issue番号（未指定時は新規Issueを作成）
- `asana_url`: URL — Asanaタスク（タイトル・説明・カスタムフィールドを取得、渡された場合のみ）
- `figma_url`: URL — 既存Figmaデザイン（UI要件・デザイントークンを抽出、渡された場合のみ）
- `spec_directory`: パス — 仕様書の出力先（未指定時は `docs/specs/issues/{機能カテゴリ名}/issue{issue番号}-{機能名}/` を自動採番）

## 出力
- 形式: 仕様書ファイル群（ディレクトリ） + GitHub Issue本文更新 + Spec PR
- 内容: 仕様書ディレクトリ（requirements.md / ui-design-url.md / design.md / qa-test.md）、Phase別タスク一覧を記述したGitHub Issue、および仕様書をまとめたSpec PRのURL

## 依存スキル
| 依存スキル | 条件 |
|-----------|------|
| `einja-skill-first` | Phase 0.5 でSkill作成必要性を評価するとき（スキップ基準非該当時） |
| `_einja-worktree-guide` | Phase 0.4 でワークツリーをセットアップするとき（常時） |
| `einja-review-spec` | 各Phase成果物のレビューゲート（Phase 1/2/3 で `review_scope` を切り替えて呼ぶ） |

※ サブエージェントは Agent tool 経由で直接起動する: 事前調査（Explore / general-purpose）、requirements-generator、ui-design-generator、design-generator、qa-generator、tasks-generator、tasks-validator。
```
