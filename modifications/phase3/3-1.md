### 主要な変更

#### direnv.ts の追加機能

```typescript
/**
 * direnv allowの確認プロンプトを表示し、実行する
 *
 * AC-003-4: 確認後 `direnv allow` が実行される
 */
export async function promptDirenvAllow(targetDir: string): Promise<void> {
  try {
    const { shouldAllow } = await inquirer.prompt([
      {
        type: "confirm",
        name: "shouldAllow",
        message: "direnv allow を実行しますか？（環境変数を有効化します）",
        default: true,
      },
    ]);

    if (shouldAllow) {
      try {
        execSync("direnv allow", { cwd: targetDir, stdio: "inherit" });
        logger.success("direnv allow を実行しました");
      } catch (error) {
        logger.warn("direnv allow の実行に失敗しました");
        logger.info("後で手動で 'direnv allow' を実行してください");
      }
    } else {
      logger.info("direnv allow をスキップしました");
      logger.info("後で手動で 'direnv allow' を実行してください");
    }
  } catch (error) {
    // プロンプトがキャンセルされた場合など
    logger.info("direnv allow をスキップしました");
  }
}
```

### 実装メモ

#### 使用した技術
- TypeScript オプショナルチェーン (`?.`)
- Vitest テスト設定（concurrent オプション）
- Node.js ファイルシステム操作（rmSync のリトライ機能）

#### 重要な決定事項

1. **テストのシーケンシャル実行**: ファイルシステムの競合を避けるため、generateTemplate のテストは並列実行を無効化しました
2. **リトライロジック**: ファイルシステムの非同期性（特にmacOS）を考慮し、削除処理にリトライ機能を追加しました
3. **テストファイル追跡**: 実テンプレートへの書き込みは避けられないため、確実にクリーンアップする仕組みを導入しました
4. **エラーハンドリング**: クリーンアップ失敗時もテストが継続できるよう、警告のみ表示する設計にしました

#### 技術的な背景

**型チェックエラーの原因**:
- TypeScriptは配列アクセス `arr[0]` が `undefined` を返す可能性を認識する
- オプショナルチェーンを使用しても、その後の配列アクセスには適用されない
- 正しい記法: `obj?.arr?.[0]?.prop`

**ファイルシステム競合の原因**:
- Vitestはデフォルトでテストを並列実行する
- 複数テストが同じディレクトリ（test-temp）を同時に操作すると競合が発生
- macOSのAPFSファイルシステムは削除が非同期的に完了する場合がある

**解決アプローチ**:
- シーケンシャル実行により競合を根本的に回避
- リトライロジックでファイルシステムの遅延に対応
- テストファイルの明示的追跡で確実なクリーンアップを実現
